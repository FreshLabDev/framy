# framy: design

Written on 26 October 2026, before the code, and updated as framy was built. The research behind it is in [research/](research/README.md) (in Russian, with sources).

framy makes images and videos with the models of OpenRouter, OpenAI and Google. The website is the main interface; almost everything it does can also be done in the Mini App and in an ordinary Telegram chat. framy pays for a small free allowance; everything beyond it runs on the person's own keys, at the provider's price, with nothing added on top.

Marks used below: **(owner)** is a decision of the owner, of 26 October 2026 unless it names another day; **Proposal** is mine and still open to change.

## Principles

| Need | framy approach |
|:--|:--|
| One place to make an image or a video | A site with one prompt line and every model the person's keys unlock |
| Honest price | The provider's price before every run, in USD and in the person's currency; the actual cost after |
| Telegram is not an afterthought | `/img` and `/edit` in any group, whole albums as input, a preview to confirm, the result in place |
| Models change every month | The catalog is data pulled from OpenRouter every hour, not code |
| framy is not a credit reseller | Free: 5 images a day and 1 video a week **(owner)**; the rest on the person's keys **(owner)** |
| Familiar stack | Go, the family's `tg` client, shared Asterfield `core`, one service on ws04 |

## Surfaces

| Surface | What it does | Stage |
|:--|:--|:--|
| Site | Composer, model picker, history, settings, provider connections. The main interface **(owner)** | 1 |
| Mini App | The same frontend on the same origin, opened from the bot | 1, polished in 3 |
| Group chat | `/img` and `/edit` with a preview, confirmation, progress and the result in the chat **(owner)** | 1 |
| DM | The same as a group, plus settings and delivery of results made on the site | 1 |
| Inline mode | The person's past results by `file_id`, a button to the bot's chat, whose panel opens the Mini App | 3 |
| Guest mode | `@framyin_bot …` in reply to a photo in a chat where framy is not a member | 3 |

## Accounts

One account per Telegram user id. It is the same number in a bot update (`from.id`), in the Mini App (`initData.user.id`) and on the site (the `id` claim of Telegram Login, not `sub`), so nothing needs linking.

- **Site.** Telegram Login through OpenID Connect at `oauth.telegram.org`: authorization code with PKCE, scopes `openid profile telegram:bot_access`. The last scope lets the bot write to the person's DM, so a result made on the site can arrive in Telegram. The `id_token` is checked against the JWKS (`iss`, `aud` = client id, `exp`). The flow is a server-side redirect with `coreos/go-oidc` and `x/oauth2`, which worked against Telegram's live discovery document. Three details:
  - `AuthStyleInHeader` set explicitly;
  - `SupportedSigningAlgs: RS256` (the provider also lists ES256K);
  - the nonce and the state checked by framy itself, since `Verify` does not check the nonce.

  Telegram issues no refresh token, so framy keeps its own session: a `__Host-` cookie, `HttpOnly; Secure; SameSite=Lax`, with only a hash of the session id in the database. The popup widget is not used: it breaks under `Cross-Origin-Opener-Policy: same-origin`.

  This is `internal/auth`. `GET /auth/login` keeps the state, the nonce and the PKCE verifier in a ten-minute `__Host-` cookie (a table would need a write for every visitor), and `GET /auth/callback` finds its sign-in there by the state and takes it out whatever happens. The cookie holds the browser's last three sign-ins, not one, so two tabs, or Sign in pressed again while Telegram's page was slow, each finish on their own; a callback with a state the cookie does not hold fails and leaves the others in it. The cookie is signed with HMAC-SHA256 under a key derived from the client secret (HKDF), so it survives a restart and a browser can carry it but not write it: the checks of the state and the nonce compare what Telegram sent back with what framy made, never with what a client chose. Unsigned, someone holding another person's code and the state and nonce of that sign-in (a callback address in a history or a proxy's log) could write a cookie to match, with only Telegram's check of the PKCE verifier in the way. A cookie framy did not sign returns to `/?sign_in=expired`. A refused sign-in sets no session and returns to `/?sign_in=cancelled`, `expired`, `failed` or `unavailable` (Telegram's discovery document cannot be read, or too many tries from one address), which the site says in the person's language; one that succeeds ends the session the browser had, so signing in again, or as someone else, leaves no older session open behind it, and a copy of the old cookie stops working. A session lasts 30 days from the last time the site loaded the person: `GET /api/me`, at every visit and on coming back to the tab, moves its end to 30 days from then, in the database and in the cookie's `Max-Age`, when it was last moved more than a day ago, so it costs one write a day at most. A renewal also calls `core.touch` with the person's id alone, as a sign-in does with the whole card, so the family's presence goes on with the session instead of stopping at the last sign-in. Someone who comes back within a month is never signed out in the middle of their work, and a session nobody uses ends; one that got out lives as long as it is used, which is what Sign out everywhere is for. The photo is the link of the last sign-in, which such a session may outlive; the site shows the initial of the name when it no longer loads. `POST /auth/logout` ends one session, `POST /auth/logout/all` every session and token of the person, and a person's deletion takes theirs with it. The site's settings have both beside "Signed in with Telegram": Sign out and Sign out everywhere, which asks first and signs nobody out on the page until the server has ended them, so a cookie or token that got out does not stay open behind a page that says it is closed. A logout the session store fails answers 503 and keeps the cookie, and the site then says the person is still signed in and keeps them so; it says they signed out only on the 204, so nobody leaves a shared computer with the account still open. A press still sending its files stops there, a clip to the bucket included. `return_to` is a path on the site or nothing. Without `TELEGRAM_LOGIN_CLIENT_ID` and `TELEGRAM_LOGIN_CLIENT_SECRET` (and `SITE_URL`, which makes the redirect URI) the two site routes send the browser to `/?sign_in=unavailable` and the rest runs.
- **Mini App.** `initData` is checked with HMAC as in `maply/internal/auth`, with `auth_date` at most an hour old. The server answers with a short-lived bearer token, because cookies in the Telegram Web iframe are unreliable. Since 20 July 2026 Mini App methods work only on the registered origin, so the site and the Mini App share one origin and one frontend.

  The page believes the `tgWebAppData` of its address only inside Telegram: a native client gives it its bridge before any script runs (`TelegramWebviewProxy`, or `external.notify` on old Windows clients), and Telegram Web shows it in a frame, which `frame-ancestors` allows nobody else. A link with someone else's launch data opened in a browser stays the site, so nothing done in that tab, a key pasted in the settings least of all, lands in their account. The settings name the account they belong to, with its Telegram picture, on the site and in the Mini App. On `localhost` the address alone emulates the Mini App, for development.

  `POST /auth/miniapp` takes `{"init_data": "<raw string>"}` and answers `{token, token_type, expires_in, user_id}`; the token is stored as a hash like the cookie and ends when its `initData` stops being accepted, an hour after `auth_date`, so `expires_in` is under an hour for `initData` exchanged late, and `initData` with less than a minute left is `init_data_expired` already. One `initData` that got out is good for an hour after Telegram signed it, not an hour after its last exchange. One launch gets one token: the process keeps it by the `initData`'s hash while it lasts, and the same `initData` sent again, in whatever order or escaping, gets the same token back with nothing written: trading it again costs neither a row nor a write to `core.person`. A token that was signed out, here or everywhere, is not given out again; the launch then gets a new one. Two exchanges of one launch at once wait for each other, so they make one token between them, and after a restart the launch makes one more. Telegram signs `initData` only when the Mini App opens, so one left open for more than an hour has to be opened again. Once framy refuses it (`init_data_expired`, or `init_data_invalid`), the page calls the session over: it asks framy nothing more as that person and trades nothing again, says once why the Mini App has to be opened anew, and its main button closes it (`Telegram.WebApp.close`). What is typed from then on is kept as it is typed, since Telegram's own close button or a swipe may close the Mini App without the page hearing it, and comes back in the prompt on the next open (a day at most, in `localStorage`). A run on the stage then says it goes on on the server. It needs only the bot token, not the Login client.
- **Name and photo.** framy holds no `SELECT` on `core.person`, so every sign-in writes the name and photo Telegram gave into `framy.profile` (migration 012), over what was there: the `name` claim (else given and family name, else `preferred_username`) on the site, `first_name last_name` (else `username`) in the Mini App. The photo stays Telegram's link, not a copy, and only an https link on `t.me` or `*.telesco.pe`, where `t.me` redirects, is kept: they are the only Telegram hosts the site's `img-src` allows. A failed write is logged and the sign-in goes on. `GET /api/me` gives them to the frontend.
- **For code that needs the person.** `Auth.Person(r)` gives the Telegram user id from the cookie or from `Authorization: Bearer`, from a 30-second cache or one query on the primary key; a request with a bearer token is judged by it alone. Ending sessions notifies `framy_sessions` as it commits, with nothing in the notice, and every process of framy (the other stack, the old process during a deploy) empties its cache on it and each time its event listener connects, so a session ended anywhere is refused everywhere at once; the 30 s are left only for a notice missed while the listener reconnects. A database that does not answer counts as nobody for `Person`; `Auth.Identify(r)` says it apart as an error. `Auth.Require(h)` answers 401 `{"error":"sign_in"}` to nobody and 503 `{"error":"unavailable"}` when it cannot tell, and `Auth.PersonKey` is `Person` for `web.Config.Person`, so the per-person rate limits count the signed-in.
- **Signed out.** The site shows the composer, the catalog and prices. "Create" asks to sign in ("Sign in to create"), and goes at once, with nothing typed yet; the line under the price says what signing in gives (5 free a day, 1 free a week for a video), and what is typed before it comes back after it. Only a 401 from `GET /api/me` says nobody is signed in: when it fails otherwise as the page opens (a 5xx, the tunnel, the network), the page does not know, offers no sign-in to a person who may be signed in already, says framy is out of reach and asks again, after 2 s and then twice as late each time up to a minute, until framy answers. The Mini App's token ends with its launch, an hour after Telegram signed it, and its `initData` then buys no other: a run pressed after that, a form of the settings or the next read of the person says to close framy and open it again (`init_data_expired`), once, instead of a code or a page that only shows nobody signed in. The library and a run's address (`/r/<id>`) ask to sign in too, with a way to the composer beside it, and framy's mark in the header leads to the composer from any page. Signing in keeps the composer: the words, the kind, the model the person picked (one they did not pick gives way to their default), the payments, the settings, the frames, the part of a clip and the files come back after Telegram's page, and the same holds for connecting OpenRouter and for a new language. A file framy keeps goes by its id; one still in the browser waits in its IndexedDB for the load, up to 100 MB in all, and is deleted when it is back, when the browser brings the page back from its cache instead (the back button from Telegram's page), or on a later visit once an hour has passed. A file that did not come back is said ("Add the files again"), so nobody presses Create on less than they put together.

## Providers and keys

Each run uses one **offer**: a model at a provider, paid either by the free allowance or by one of the person's connections.

| Provider | Connect | Check on save | What it unlocks |
|:--|:--|:--|:--|
| OpenRouter | "Connect" button: OAuth PKCE, no app registration; pasting a key as a fallback | `GET /api/v1/key` | about 60 image models and 30 video models (63 and 33 on 5 November 2026, Omni 1.1 and 1.2 Flash among them) |
| OpenAI | Paste a key from an account with credits | `GET /v1/models` | `gpt-image-2.6-sunburst`, `gpt-image-2.6-flare`, `gpt-image-2.5-sunburst`, `gpt-image-2.5-flare`, `gpt-image-2`; no video, Sora closed on 24 September 2026 |
| Gemini | Paste a key from a project with billing | `GET /v1beta/models` | Nano Banana 2.1, 3.1 Flash, 3.1 Flash Lite, 3 Pro; video only `gemini-omni-1.1-flash` |

A person meets each provider under one name, on the site, in the bot and in the chat, the same in every language (`catalog.ProviderName`, and `PNAME` in the site's `catalog.js`, which a test keeps equal). Google's is **AI Studio**, where its key is made and its billing is turned on, with AI Studio's mark on the site; the code, the catalog and the logs call it Gemini, after its API.

OpenRouter OAuth (`internal/oauth`, `SITE_URL` for the callback, a KEK file for the key):

- `GET /oauth/openrouter/start` for a signed-in person makes a random `code_verifier` and `state`, keeps the verifier and a hash of the state in `oauth_state` for 10 minutes (one open flow per person; starting again replaces it), puts the state in a `__Host-` cookie too (`HttpOnly; Secure; SameSite=Lax`), and redirects to `openrouter.ai/auth` with the S256 challenge, `state`, `key_label=framy` and `callback_url=<SITE_URL>/oauth/openrouter/callback`. Nobody signed in: a redirect to `/auth/login?return_to=/oauth/openrouter/start`. It is a GET because `openLink` and the redirect after sign-in cannot post; it only opens a flow of the visitor's own, bound to their own browser by the cookie.
- A callback with a `state` that is not the cookie's answers a flow this browser no longer holds, the one a newer start replaced in another tab: it ends `expired` and touches neither the cookie nor the newer flow, which its own tab still finishes. Otherwise the callback spends the flow of the cookie's state first, whatever follows, then needs the person signed in now to be the person who started it. An answer without a code, the person's refusal or an error of OpenRouter's, ends the flow as it says (`cancelled`, `refused`): OpenRouter does not send the state back when the person denies access, and such an answer saves nothing. An answer with a code needs the `state` in the URL to equal the cookie and the flow to be under 10 minutes old. The cookie ties the end of a flow to the browser that started it, so a state that leaked in a URL or a log finishes nothing; with the code's PKCE verifier and the person check, a callback built by someone else gets no key.
- Then it exchanges the code at `POST /api/v1/auth/keys` and saves the ordinary `sk-or-v1-…` key through `keys.Service.Save` (checked with `GET /api/v1/key`, encrypted, paid from the person's credits). It replaces a key the person had, pasted or not. No code, verifier or key is logged, or put in a URL or an error.
- Every callback ends in a redirect to the site: `/?connect=openrouter&result=<result>`, with `connected`, `cancelled`, `expired` (no flow this browser can finish: older than 10 minutes, replaced, used, or someone else's), `signin` (nobody signed in), `refused` (OpenRouter or the key check said no) or `unavailable` (OpenRouter or framy failed, or too many tries from one address: try in a few minutes). The frontend reads it, removes it from the address and shows the settings. Disconnecting is `keys.Service.Delete`; the person revokes the key at openrouter.ai/settings/keys, since OpenRouter has no revoke without a management key.
- In the Mini App the flow opens in the external browser through `openLink`, where nobody may be signed in to framy. A second sign-in there was the hardest step of connecting, so the link carries a ticket instead (#489): `POST /oauth/openrouter/ticket`, for the person signed in in the Mini App, keeps the hash of a random ticket in `oauth_ticket` for 5 minutes (one per person; asking again replaces it) and answers `{url, expires_at}`, the start's address with `?ticket=`. The Mini App asks for it as soon as Connect shows, since Telegram opens a link only straight from a tap and not after a request, and asks again after 4 minutes; without one in hand the link is the plain start, which asks to sign in as before. The start spends the ticket first, whatever follows, refuses one that expired and one brought to a browser where another person is signed in (`expired`), and opens the flow for the ticket's person, marked `ticketed`. The callback of a ticketed flow takes a browser nobody is signed in on, and one where another person is still ends `expired`; the cookie, PKCE and the single use hold as for every flow. Its result has `&from=telegram`, and the site says, signed in or not, how it ended and that the tab can be closed for Telegram. What a ticket risks: whoever opens it first gets the flow, so a stranger who learned it and used it first could connect their own OpenRouter account to the person's framy and then see the person's prompts in that account's activity. So it lives minutes, is spent by its first use, travels only in the link the Mini App hands to Telegram, never in a message, and is in no log line.

This button is the main door for people without keys, so it gets built first and tested end to end.

A connection has a status that framy can actually back up:

| Status | Meaning |
|:--|:--|
| `valid` | The key passed the check above |
| `verified` | A generation succeeded on it |
| `needs_billing` | Gemini answered 429 with `limit: 0`: the project has no billing |
| `needs_verification` | OpenAI answered 403 about organization verification |
| `no_credits` | OpenRouter 402 or OpenAI `insufficient_quota` |
| `invalid` | 401; the key was revoked or mistyped |

The Gemini adapter proves three of them. A 429 with `limit: 0` (or a quota value of 0), and a 400 `failed_precondition` that asks to enable billing, come back as class `key` with status `needs_billing`; a 402 or "prepayment credits are depleted" as class `money` with `no_credits`; a 401 or `API_KEY_INVALID` as class `key` with `invalid`. None is retried. A 429 with a limit above 0 is a wait and is. A 400 that says "User location is not supported" is about framy's server, not the key: class `region`, as OpenAI's `unsupported_country_region_territory` is. Nothing ran, so nothing is charged; the key's status is left alone, the person is told to pick a model of another provider, and the worker logs it as an error, since every run on that provider fails until the server's address changes.

The check on save can say only two things. A key the provider refuses (a 401, Gemini's 400 `API_KEY_INVALID`) is not stored. A key it accepts is stored as `valid`, which claims no more than that the list of models answered: a key without billing, verification or credit lists models too. So `needs_billing`, `needs_verification` and `no_credits` come from the failure of a run, when the adapter's error says so (a Money error alone means `no_credits`, except at Gemini, where a 429 is a quota as often as a missing billing account), and `verified` from the success of one. A 403 on the list is not stored either: the key may be restricted to other calls, and the list is all the check sees. A check that reached no answer (a 429, a 5xx, the network) stores nothing. Nor does one the provider refused for the country framy's server is in (Gemini's 400 "User location is not supported", OpenAI's 403 `unsupported_country_region_territory`): the answer is `key_region`, which says so, where the person would otherwise be sent to the key's settings or told to try again in 10 seconds. "Re-check" asks again: a refusal makes the key `invalid`, an acceptance makes any status that named a problem `valid` again and leaves `verified` alone, since the person who fixed the account presses it and the next run sets the status again if it was not fixed. A key marked `invalid` is not used until it is replaced or re-checked; the other statuses still run, since a refused run costs nothing and is how they heal. Since the check cannot see billing or credits, the settings say before a key is connected what it needs to make anything: OpenRouter's row that runs are paid with its credits, OpenAI's that the account needs credits, AI Studio's that it needs a project with billing.

Nobody can read the balance behind an OpenAI or Gemini key. For OpenRouter, `/api/v1/key` gives what was spent through the key and what is left of its limit, and that is all framy shows.

**Keys at rest.** Envelope encryption with the standard library: a data key per record, AES-256-GCM through `cipher.NewGCMWithRandomNonce` (Go 1.24+), the data key wrapped by a key-encryption key with the same cipher. The associated data is `user_id | provider | connection_id` for the key and `user_id | provider | connection_id | kek_version` for the wrap. The version is bound where the KEK is used: bound into the key's own ciphertext, it would make every rotation encrypt every key again. The KEK is a file secret with mode 0400 (`FRAMY_KEK_FILE`; a `FRAMY_KEK` variable is refused; a file that group or others can read stops the start on every stack, and only `FRAMY_KEK_ALLOW_LOOSE=true`, for a laptop, lets it through with a warning), not an environment variable that `docker inspect` shows, and it is kept apart from the database backups (Backups, below): a dump and its KEK together give away every stored key, and losing the KEK loses them all. The file has a line per version, `<version>:<base64 of 32 bytes>`; the highest wraps new data keys, and an older line stays while a row still uses it. Rotation rewraps the data keys only and leaves the encrypted keys as they are, and only production does it, at start: the test bot keeps a copy of the same file, and since the table is one for both (Stacks), a rotation from a copy that had a line production lacks would leave production unable to open any key. So a rotation starts on production: add the next line to its file and restart it, and it rewraps every data key and logs how many; then copy the file to the test bot and restart that, and replace the copy kept apart from the backups. In between, the test bot cannot open the rewrapped keys, but production never holds a key it cannot open, as it would if the test bot had the new line first and saved a key under it. Once neither start reports keys on the old version, remove the old line from both files. The test bot only counts: it logs an error when a row is wrapped under a version its file lacks and a warning while rows wait on an older one. Tink is not used: its documentation has no recipe for a local KEK. The person sees the last four characters. A stored key is decrypted only to be sent to its provider: for a run, in the worker, and when the person presses Check in the settings. The decrypted bytes and the data key are zeroed as soon as the call has its copy, but Go cannot wipe a string: the key the adapter puts in its request header, and the copies `net/http` makes of it, stay in the process's memory until the garbage collector reuses it, which may be well after the request. What guards that memory is the container: it runs as an unprivileged user with every capability dropped and `no-new-privileges`, so nothing in it can attach a debugger, and a Go crash prints a traceback and writes no core dump (`GOTRACEBACK` is left at its default; `crash` would make one). Whoever is root on the host can read it, as they can read the KEK. A key never reaches a browser, the Mini App or a log. There is one connection per person and provider, and a key pasted over another is a new connection, so what a run reports about a key cannot land on the one that replaced it. Deleting a connection deletes the row; revoking the key at the provider is the person's step, and the settings page says so. A key a video sent within the hour (`jobs.RunDeadline`) still needs is not deleted: framy asks about the video and fetches it with that key, the run is likely paid, and the delete answers `key_in_use` until the video is in. Pasting another key over it is not refused, since a leaked key must be replaceable at once; whether another key of the same account fetches the video is not checked. The adapters take their key from `keys.Service.JobKey`, which refuses a free run, since framy's key pays for it, and a key the provider has refused, except to ask about a run already sent: asking costs nothing, and the refusal may have been passing.

**Keys in chat.** Keys are entered on the site or in the Mini App only. A message in a DM that looks like a key (`sk-` followed by a long random run, which covers `sk-proj-` and `sk-or-v1-`, or `AIza`) is deleted at once, and so is a message edited to hold one; nothing is saved, and the bot answers in the person's language in three short sentences: what happened to the message, that a real key is exposed and is to be revoked and replaced, which matters most, and that keys go in the settings, on the site or in the Mini App. If Telegram refuses the delete, the first sentence says that and asks the person to delete it, instead of claiming it. Under the answer is the way to the settings at the provider the key looks like it is for (`keys.KeyIn`: OpenRouter for `sk-or-`, Gemini for `AIza`, OpenAI for any other `sk-`, the top of the settings for Anthropic's `sk-ant-`): the Mini App in the DM, framy's DM with `/start settings_<provider>` elsewhere. The same holds for what is sent to framy outside the DM (`internal/chat/keyguard.go`), before anything of it is kept, priced or sent to a model: `/img` or `/edit` in a group with a key in its text or caption is deleted where framy may delete it, and answered as in the DM; a guest message cannot be deleted by framy, so its one answer asks the person to delete it. A group message that is not to framy is none of framy's business, admin or not. On the site a prompt with a key is refused before a job (`key_in_prompt`), and the stage says the key went no further than framy, with the way to its settings. An inline query is not checked: it is a search of the person's own library, kept nowhere and sent to no model, and Telegram gives nothing to delete. `framy_keys_in_chat_total` counts them all.

**Keys in the settings.** The field of a key is hidden as a password's, and asks password managers not to offer or keep it. A key the provider refused stays in the field to be fixed, as its value only, never as an attribute, so it does not stand in the page's markup for an extension, a page translator or a report of the page to read; it is not kept anywhere else in the browser.

Who pays in a chat: always the person who sent the command, from their free allowance or their own connections, never another member's.

## Model catalog

### Sources

- OpenRouter publishes its catalogs without a key: `GET /api/v1/images/models`, `GET /api/v1/images/models/{id}/endpoints` (the exact price per endpoint) and `GET /api/v1/videos/models`. Only `GET /api/v1/models` carries `expiration_date`, and only `GET /api/v1/models/{id}/endpoints` carries a discount off the listed price (`pricing.discount`, per upstream), so both are read too. framy pulls all of them every hour, about 155 requests.
- Direct OpenAI and Gemini have no such catalog. Their models are described by hand in the repository in the same schema (`catalog/openai.yaml`, `catalog/gemini.yaml`).
- An overlay file (`catalog/overlay.yaml`) adds what no API says: which offers are the same model, reference limits by kind for video, which models accept `previous_job_id`, pass-through parameters with their allowed values, the face policy, display names, the effort mapping, the featured flag, the free-tier flag, and what the model picker reads: families, fast modes, suggestions and one name per maker (Model picker).

### Models and offers

A model such as Nano Banana 2.1 has offers `gemini:gemini-nano-banana-2.1` and `openrouter:google/gemini-nano-banana-2.1`. The overlay maps them explicitly; names are not guessed. A model's id is its OpenRouter id, so it stays when a direct offer joins later; a model OpenRouter does not carry, such as Gemini Omni, gets its id in the overlay.

The sync never deletes. An offer that leaves its source gets `disabled_at`, and a model with no offer left is disabled with it; one that comes back is restored. A failed listing changes nothing, and so does one where more than half the entries do not decode. A model whose entry does not decode, in any of the three listings, or whose endpoints fail, keeps its last row, and the sync logs why (`catalog offer not refreshed`): one field OpenRouter changes on one model holds back that model only. A sync that would disable more than half of OpenRouter's offers is refused as a broken answer.

Prices of the same model at different providers are usually equal: OpenRouter charges the provider's price per request and takes its fee of about 5.5% when credits are bought. What differs is where the money comes from and which settings exist:

- only direct Gemini has `thinking_level`, Google Search and Image Search grounding, `media_resolution`, JPEG output and a video as an input to Nano Banana;
- only direct OpenAI has the mask, any `size` up to 3840 px and GPT Image 2.6's `complexity`.

The picker shows each connected offer as its own row: price, provider, and what the offer adds.

### Parameters become controls

Every OpenRouter model describes its parameters as `enum`, `range` or `boolean`, and the hand-written descriptors use the same form. The composer draws controls from them:

| Kind | Control |
|:--|:--|
| `enum` of up to 6 values | segmented control |
| longer `enum` | dropdown |
| `range` | stepper or slider within the range |
| `boolean` | toggle |

A parameter the model does not list is not shown at all, not shown disabled. When the model changes, a value the new model does not allow falls back to its default. Not built yet (#19): a short note saying which setting fell back; today the control simply shows the new value.

### Defaults

No catalog gives defaults, so one rule in Go (`catalog.Defaults`) picks the value of a setting nobody chose. `GET /api/catalog` lists them per offer, `POST /api/quote` fills them in and prices them, and a run on the person's key goes with them, so what is priced is what is sent. A free run goes with its plan's settings only.

- Aspect ratio: the shape of the first attached photo or video, `auto` where the model keeps it itself; with no file, the nearest to 1:1 for an image and to 16:9 for a video.
- Size, where a model has it instead of an aspect ratio: the same shape at about 1024×1024. A video's `size` gets none, since OpenRouter refuses it next to a resolution or an aspect ratio.
- Resolution: the smallest that reaches 1K for an image or 720p for a video, else the largest.
- Duration: the shortest of at least 5 seconds, else the longest.
- Quality: `medium`, else `standard`; background: `auto`; complexity: `high`, OpenAI's own default; any other choice: what the provider does without the field where the hand-written descriptor says so (`default:` on the parameter), else `auto`, else the first, which for an effort is the least. Nano Banana 2.1 thinks at `medium` as it does at Google, so a result is never worse than the maker's own, as with input detail; the 3.1 models start on `minimal`, which is Google's default for them.
- One result; sound on, as OpenRouter has it; Google Search off; any other range in its middle.

Only the settings the composer draws get a default; the rest stay the provider's. Nor does a setting one of OpenRouter's upstreams would not take with that value: sending it would narrow the upstreams OpenRouter may try, while the estimate counts the cheapest.

### Hidden

- `heygen/avatar-iv`, a talking head from a photo and a voice, until the composer takes a voice.

### Watching the makers' lists

framy has no key of OpenAI's own, so it cannot ask `GET /v1/models` on a schedule. It reads the answer at the moments it already asks for it: every time a person saves or rechecks an OpenAI key and the check passes (`keys.Config.Listed`). The comparison with `catalog/` (`Files.ListedNotes`) says two things, each once per process, in the log of every stack and in the operator chat from production:

- OpenAI lists a `gpt-image-*` that `catalog/openai.yaml` does not describe and the overlay does not hide: a new GPT Image (GPT Image 2.6 came out on 4 November 2026 with nothing in the logs). A dated snapshot of a known model, the closing GPT Image 1 line the overlay hides, and a model whose shutdown day has passed are not news.
- A described model has a `shutdown_date` the overlay lacks or has differently: the note says to set `deprecated.shuts_down`, which is what makes the picker stop offering the model 14 days before.

Nothing hides a model by itself: the list is one person's account, and the decision is written in the overlay. A watch without a person's key, such as a weekly job on a key of the operator's own, would need a secret that does not exist yet; until then a new model is noticed when someone connects or rechecks a key. Gemini's list has no shutdown field.

## Composer

One component for the site and the Mini App. On top, a large prompt line that grows with the text **(owner)**; under it, the attachments; then the model chip, the setting chips and the price next to "Create". Results appear in a feed below. On a phone the kind, the model and the settings share one row over the prompt, the settings as an icon only, and files are added in the row under the prompt in both kinds, as the slots of a video are; the row over the prompt has no second way to add one **(owner, 31 October)**. A model's name too long for its chip takes two lines on a phone rather than lose its end, and the line under the price does on any width, so a reason a press cannot go reads to its end; an empty frame too small for all it says drops its icon first. The tiles of that row scroll sideways, and the line about the files (that they stay on the device, why one is not used) stands beside them while it fits and under them otherwise, never cut. On a phone the composer is a dock at the foot of the screen. A window too low for it, under 960 px wide and at most 560 px high (a phone on its side; with a mouse, a page zoomed in or a small window, whichever way the screen stands), has the composer in the page over the stage instead, and the page scrolls: a run that starts brings the stage into view, and Edit the prompt, Continue and Another model bring the composer back. A phone held upright keeps the dock, and a keyboard that shortens the window while a field is typed in does not switch the layout.

### Frames

One press of Create can make several results, each with its own model, payer and settings, so models are compared side by side **(owner, 31 October)**. The composer calls them frames: up to 6 pictures or 4 videos. "All" edits what every frame shares; a frame picked edits only itself, and keeps only what differs from the rest. The approved mockup is the artifact "framy composer" (`framesSec`, `previewEl`, `plan`); on the phone the frames are a swipe strip under the button that adds one, which stays on top **(owner, 31 October)**, and the settings of one frame swipe to the next, the strip rolling with them. In Arabic the strip runs right to left, and a swipe to the right brings the next frame.

framy, not the browser, decides how many jobs a press is (`POST /api/batches`). Frames that are the same run (offer, payer, settings, prompt, files, the clip continued) go as one job with `n`, as many as the offer makes at once (`catalog.AtOnce`: the offer's `n` maximum and no more than any upstream of OpenRouter takes), and the rest go on to the next job of that run: five at four at once are a job of four and a job of one. Free frames go one by one, since the allowance counts runs and its plan sets `n`. The jobs of a press share a `batch`, and each says which frame each of its results is (`batch_frames`); the library shows the press as one run, and Take the prompt brings every frame back.

### Model picker

Two tabs, Images and Video, with search. The suggestions for what is attached come first, then the featured models. A row shows:

- the model and its maker;
- what it can do: references, 4K, sound, last frame;
- the price for the current settings in USD and the person's currency;
- one line per connected provider.

What a model can do is never cut short: the facts of a row wrap, and only between two facts, and on a phone the line under the price ("or from $0.095 with a key") takes two lines rather than the facts' room. On a phone the suggestions are rows as the families are, in the same type: the name a label, the price a figure.

On a wide screen the card on the right shows the family under the mouse or the one the keyboard is on: its row, a variant or a suggestion. With a mouse the picker opens with the search in focus, to type in at once; on a touch screen it does not, so no keyboard comes up over the list. A screen reader hears a row with its facts and price, and a variant by its whole name ("FLUX 2 Max") with its price, an outdated one also that it is outdated. A model chosen gives the focus back to the model in the composer.

Proposal: models that need a provider the person has not connected stay in the list, dimmed, with "Connect OpenRouter", so it is visible what a key would unlock.

In a video the list shows only the models that can take what is in the slots (Video, below): a last frame leaves out the models with no last frame, four references the models that take fewer, a clip the models that take none, and the composer's row of variants does the same. A model that only needs more, as an editor with no clip or mischief 1 with no picture, stays, dimmed with what it needs. Nothing else changes: it is the same page and the same list.

The overlay gives the picker its shape, so a new model needs no code:

- **Families.** A model names its family, generation, tier and label: FLUX 3 Klein is family `flux`, generation 3, tier `klein`, label "3 Klein". A family is one row with its variants inside; a model of no family is a row of its own. Recraft also has a line (`base`, `utility`, `styles`) and a format (`raster`, `vector`). The overlay orders the tiers, least first, and may name the variant a family opens on, else its first featured one.
- **Outdated** is computed, never written: a newer generation of the family at the same tier, line and format takes a variant's place, and a plain variant (tier `std`, such as GPT Image 2) gives way to the newest of any tier. Nano Banana 2.1 outdates Nano Banana 2 but not Nano Banana Pro. Only shown models count. `family.keep` says why a variant stays current anyway: Seedance 2.0 makes 1080p and 4K, which 2.5 does not through OpenRouter; Qwen Image 2.1 came out after 3.
- **Deprecated.** The maker's word that a model goes away is written as `deprecated`, with the day it shuts down when the maker gave one and the successor it names. A deprecated variant gives way to that successor when it is in the same family, a family never opens on one while another variant is current, and a shutdown day closer than `hide_expiring_within_days` hides the model, as OpenRouter's leaving day hides an offer. `GET /api/catalog` says `deprecated`, `shuts_down` and `successor`. The site writes the shut-down day as the maker named it, the same day in every time zone, with its year when that is not this one.
- **Fast modes.** Wan 3.0 Prime is Wan 3.0 itself, faster and dearer (OpenRouter: "the fast-mode variant of Wan 3.0"), so it is a switch in Wan 3.0's settings, priced as Prime, and not a variant. Veo 3.1 Fast and Seedance 2.0 Fast are lighter models at a lower price and stay variants.
- **Suggestions** by situation, best first: an image, an image from more than five photos, a video, a video made from an attached one.
- **One name per maker.** OpenRouter writes xAI and SpaceXAI for the company now called SpaceXSI, and ByteDance and ByteDance Seed; the overlay maps them to SpaceXSI and ByteDance. Display names fix what OpenRouter leaves bare: Kling's "Video v3.0 Pro" is Kling Video 3.0 Pro, MiniMax's "H3 Max" Hailuo H3 Max.
- **Notes.** A variant's short line ("Faster and cheaper than MAI-Image 2.6, similar quality") is interface text, so it lives in i18n as `note.<model id>`, in every language, and only says what the provider's description, parameters or price support. The site and the Mini App take the notes from their own lines, which the build bundles with the `web.*` ones, so a note is always in the language the page speaks, also when the catalog was asked without the person (the inline boot script asks before the Mini App has its token) or the browser's first language is one framy does not speak; the catalog's `note` is the fallback for a model newer than the bundle. It says a fact that sets the variant apart in its row, not a rank that ages ("Newest", "Cheapest", "Earlier version"), and a comparison names what it compares with: the other variant's label, with the family's name when the label is a bare number ("than 2.1 Pro", "than Seedance 2.0"). An approximation is "~". A note is read only in the family's row (the picker's list of current variants, the line under the composer's card), so every current variant of a family with more than one shown model has one, and an outdated variant, a model alone in its family and a hidden one have none (`TestEveryVariantInARowHasANote`).
- **The provider's description** is OpenRouter's, in English, and the card on the right shows it only in the English page; in another language the facts and the notes say what a model does. The catalog keeps its whole sentences: OpenRouter cuts a description at its length, and the sentence it cut is dropped, not shown broken off. A sentence about the provider's price or API parameters goes too, since framy shows its own price and its own controls.

- **Duration.** Chips for discrete sets such as Veo's 4, 6 and 8 s (8 s alone while References hold a picture), a slider for ranges such as Wan's 2–30 s.

Nobody reports progress in percent. The wait shows elapsed time and the model's typical time, measured by framy from its own runs: `typical_seconds` of an offer in `GET /api/catalog`, the median from queued to done of its runs that went well in the last 30 days, rounded up, given once there are at least 5. An offer with fewer borrows from its closest kin with 5: its model's runs on every provider (the same model through the person's own key), then its family's models of the same tier and kind on its provider (`traits.family`, as the picker groups them), so the next Wan of a tier, or GPT Image through the person's OpenAI key, shows a wait before it has runs of its own. Another tier, another provider or a picture for a video is not the same speed and lends nothing. A row whose times are out of order (queued before it was made, as a test row moved back by hand) is left out. Each process reads it once a minute, from the runs that ended done in the 30 days alone (`job_done`, migration 033), so the read does not grow with every run framy ever made. The site counts from the press (from the job's `created_at` in the library) and shows the elapsed time alone while an offer has no `typical_seconds`. A video takes minutes, so while one is being made the line in place of Cancel also says the person can leave and where it will come: their chat with framy and the library for a run of the DM, or of the site while its results go to the chat; the library for the rest of the site's runs and the Mini App's, which are not sent to the chat. The line replaces the one that only said the run could not be stopped, so nothing is added under the frame. The frame shows the bot's generating loop live in dots (`halftone.js`), at 30 frames a second, or twice a second with reduced motion; they are drawn only while they can be seen, so a stage under a sheet that hides it, behind the library or in a tab in the background costs nothing. The frame keeps one size for its shape through every state of a run, while it is made, waits, is done or failed, so nothing on the stage moves but what changed. Only when the buttons under a failure would go below the screen, or behind the dock on a phone, does it give up room, and then only the room they lack.

### Attachments stay in the browser until Create

**(owner, 27 October)**

- **Before Create.** A photo or a video dropped, pasted or picked into the composer stays in the browser: a `File` with an object URL for its thumbnail. The URL lives while the composer or the run on the stage holds the file, since Edit the prompt and Again bring a run's files back with their thumbnails; once neither does, it is revoked, so a clip of hundreds of MB does not stay in memory for the rest of the visit. The client reads what the price needs and sends only that to the quote: the type sniffed from the first bytes, the size in bytes, the picture size, and a video's length (from a `<video>` element's metadata) and frame rate (from an MP4 or QuickTime file's index; none for WebM and MKV). A clip shows in the composer once that is read, or after 8 s without it; a length the browser reads within half a minute more is shown and priced then, and after that the browser stops reading the clip, which framy reads on Create. The server answers with the price and what it will do with the file: convert it, scale it, or ask for a cut.
- **On Create** the files go up. The browser first scales a photo above 2048 px on the long side down to it, as the server would anyway, so a 48 MP photo does not cross the home uplink whole. A picture that can be transparent stays so: a PNG goes as PNG, a WebP or an AVIF as WebP (PNG in a browser that writes no WebP), and only a photo as JPEG. A GIF, which the server does not take, always goes as a PNG of its first frame, since a model takes a still. Video goes by presigned PUT into `incoming/` (see Storage).
- **A photo the browser cannot draw** is still taken: a HEIC in Chrome or Firefox, which draw none. Its size comes from its header (the primary item's `ispe`, turned by its `irot`), its cell shows a plain picture sign instead of a thumbnail, and on Create it goes up as it is, for the server to convert and scale. A file with no type, as Windows and Linux give a HEIC, is known by its name; the file dialog lists `.heic` and `.heif` for the same reason. A file that only says it is a picture and has no header to read is refused by name.
- **The server trusts no number from the browser.** It checks the real files as it does any upload (Storage) and prices the run again. When the real price is higher than the one shown, the run does not start: the composer shows the new price and waits for another press. A lower price runs as it is.
- A file picked from the history is already in R2 and goes by its id, with no upload. The Mini App works the same way.
- An upload that no job took within an hour (a press of Create that failed half way, a chat command that failed after keeping its photos) is deleted with its object. The site holds one by its id for 50 minutes at most: after that, or when framy answers `unknown_input` for it, a file the browser still has goes up again with the next press, a part of a clip is cut again and a clip's last frame (Continue) is taken from the clip again, and a run refused that way is sent once more. A file a job took is kept with that job, so time alone does not send it again. A person who comes back to the composer after an hour presses Create as before.

### Input detail

Gemini takes `media_resolution` for every input picture: `low`, `medium`, `high` or `ultra_high` cost 280, 560, 1120 or 2240 tokens on Gemini 3 and later, and `high` is the default. `ultra_high` exists only per item. A lower level costs less and sees fewer details.

- **Where.** Nano Banana is Gemini, so the setting goes to Nano Banana 2.1, 3.1 Flash, Lite and 3 Pro as well **(owner, 27 October)**: as a field of each part on the direct Gemini API, and through OpenRouter only if it passes the field on. - **How it shows.** A setting "Input detail" next to the references, with the saving beside it, only on the models where the check passed. The default is `high`, so a result is never worse than the provider's own.
- **What it saves.** Most of an image model's price is the picture it makes. One reference on Nano Banana 3 Pro saves about 1–2%; 14 references about 20%.
- **Elsewhere.** OpenAI's `gpt-image-2` has no such setting: its input is always read in full. The price estimate counts input tokens at the level chosen.
- **Sent.** The Gemini adapter sends the chosen level as `resolution` on every image and video part of the request, the Interactions API's name for it. `ultra_high` exists for pictures only (Google gives a video frame 70 tokens at `low` and `medium` and 280 at `high`, and no `ultra_high`), so a video goes with `high` when it is chosen. ### Search grounding

Nano Banana 2.1, 3.1 Flash and 3 Pro on the Gemini key can ground a picture in Google Search (`google_search`), and 2.1 and 3.1 Flash in Google Image Search as well (`image_search`). Both are off unless the person turns them on. Web search alone goes as the `google_search` tool, image search with it as `search_types: ["web_search", "image_search"]`, and image search alone as `["image_search"]`.

- **What Google asks.** A grounded answer comes with Search Suggestions, HTML and CSS Google wrote, and Google's terms for grounding ask that they be shown with the result, unchanged. The adapter takes them from the answer's `google_search_result` steps, with the queries the model sent and the pages it cited (`url_citation`), and the job keeps them in `job.grounding` (migration 016): at most 4 suggestions of 64 KiB each, 16 queries and 32 sources, only `http` and `https` links of up to 2048 bytes.
- **Where it shows.** `GET /api/jobs/{id}` and the library give a finished job's `grounding`. The site and the Mini App show it under the result and its buttons on the stage (for a press, once for each grounded job, with the numbers of its frames when the press has others), so the buttons stay in sight on the smallest phone, and beside the result in the library's viewer (`ground.js`): each suggestion in a frame of framy's own origin, then the sources as plain links in one row, only `http` and `https`. The frame keeps the page's CSP, so no inline script or `on*` handler of Google's HTML runs in it; the CSP takes no inline style either, so `srcdoc` would show the HTML without its CSS: the page parses the HTML in an inert `<template>`, takes its `<style>` and style attributes out and gives them to the frame through the CSSOM (constructable stylesheets, `style.cssText`), which the CSP does not govern, and drops scripts, handlers, forms (one would post to framy as the person), frames and links that are not `http` or `https`. The frame has no `sandbox`: WebKit runs no listener of the page on a document that may not run scripts, and the CSP the frame keeps lets no link of its own open a window, so in Safari and in Telegram on iOS and macOS a chip could not be pressed at all. The frame is as tall as Google's content and as wide as the foot, the stage keeps room for it when it sizes the result, and Google's dark styles apply, since the frame's `prefers-color-scheme` follows its `color-scheme`. A press on a chip or a source opens it in a new tab on the site and through `Telegram.WebApp.openLink` in the Mini App, never in the frame. A browser without constructable stylesheets (Safari before 16.4) shows the chips as plain links. A video never has one.
- **In chat.** A Telegram message cannot carry Google's HTML, so `/img` never turns search on: the panel offers neither toggle.
- **Price.** Google bills grounded queries past a monthly allowance (5,000 queries, then $14 per 1,000 on Gemini 3). Neither the estimate nor the actual cost counts them, since framy cannot see how much of the person's allowance is used. The composer says so next to the toggle.

## Price and currency

The composer shows the price before the run, and a run on a key does not start before it: while the bar shows "…", Create is off, for the button, Ctrl+Enter and Telegram's main button alike. A price beside a choice is the same run with no payer named, which the server prices as the run on a key, so the bar shows it as soon as the choice is picked. A price that did not come is asked again after a second, then after twice as long each time, at most 30 s apart, while the page still shows it. `internal/price` works it out from the rates of the offer's routes and the run's settings, and labels it with one of five kinds:

| Kind | Shown as | When |
|:--|:--|:--|
| `exact` | the price | the rates and the quantities are known: tables by size and quality (FLUX.3, Seedream, Krea, Qwen, Recraft, Grok, Riverflow 2), video seconds by resolution and sound, Seedance's video tokens at a size in the overlay's table |
| `about` | "about" | a formula or a rounding decides: OpenAI's and Gemini's tokens, FLUX.2's megapixels, the prompt's tokens, routes at different prices, two video rates that both fit and differ, the seconds of a reference clip as the provider measures it, a reference sound (no rate names one and no bill with one has been seen) |
| `up_to` | "up to" the most | a setting is not chosen yet, or the model picks it: Omni's 3 to 10 s, FLUX Video Upscale's factor |
| `from` | "from" the least | the provider sets the price after the run: Riverflow 2.5 |
| `unknown` | "known after the run" | nothing says how many output tokens a run makes: Omni at 1080p |

The picker prices a family, or a model with several offers, by the cheapest of them, and when they differ as "from" the least any of them costs: for an `up_to` that is its least, not the most its label names.

**Discounts.** OpenRouter takes a share off the listed price of some models, shown on the model's page as the listed price struck through: on 28 October 15% off `alibaba/wan-3.0` and 50% off `heygen/heygen-video-1`, and none on any image model; on 5 November the same two and 50% off `krea/k3-edit`. The sync keeps the discount on the route, matching an upstream by its tag, which is the provider slug of the Images API; a video model's one route takes the smallest of its upstreams'. The estimate takes the discount off the total and keeps the listed figures (`list_usd`, `list_max_usd`) for the price shown struck through; its lines stay at the listed rates. A discount that could not be read this hour is none, and one outside 0–1 is ignored, so a broken answer only makes a price dearer. OpenRouter bills the discounted price, as its page says: checked on 30 October (check 13). A rate the page marks as left out of the discount (`isDiscountExempt`), as HeyGen's rate past 15 s, is counted in full (`price.long.undiscounted`), and the share shown off a price is what the discount takes off that figure: less than the route's where part of it is at such a rate, and nothing struck through where all of it is, as HeyGen's "up to" past 15 s.

An estimate never rounds in framy's favour, and an approximate one says so. An offer with several routes is priced by the cheapest, and the dearest is the most it can cost, since OpenRouter may fall back to it. The estimate keeps its lines: each billable or SKU, its rate and the quantity.

Where OpenRouter's rates are not enough, a model's `price` in `catalog/overlay.yaml` fills in:
- `tokens`: tokens per output image by resolution (Gemini, MAI, Tencent HY Image by Tencent's price table), per second of output video (Omni), and per input image and per second of input video by the Input detail level, `*` being the provider's default (Nano Banana: 1,120 a picture, 102 a second of video, a frame and its sound, by Google's media resolution guide);
- `openai_tokens`: the base of OpenAI's formula by quality;
- `openai_token_factor`: what OpenAI's calculator multiplies the formula's tokens by, rounded, by quality: GPT Image 2.6 has 2.5's base, times 4.2 at `low` and 3.3 at `medium` (823 and 1,449 tokens at 1024×1024, where 2.5 takes 196 and 439);
- `openai_input_patches`: GPT Image 2 and 2.5 count an input image in 32 px patches, a token each, at most this many (1,536). OpenAI does not publish the count; the one worked out on OpenAI's forum, with a small image magnified to a long side of 1024 and a canvas over 3:1 counted as 3:1, matched a run on the test bot (a 1280×853 photo, 1,080 tokens);
- `input_tokens_per_mp`: tokens an input image takes per megapixel, for a model that counts them by size (MAI, about 1,050 measured, 1,100 set);
- `variants`: the settings a dearer rate or a video SKU is for, such as Krea's style references or FLUX Video Upscale's creative rate, so it is not taken otherwise;
- `skip`: a billable framy never sends, with the reason, such as Riverflow 2's fonts;
- `from`: why the price is only a floor;
- `free_images`: how many images a per-image price leaves free, which OpenRouter says only on the model's page: HeyGen Video's first 2 references, Hailuo H3's first 5 (as MiniMax bills them). The first runs with references check it against the actual cost;
- `sizes`: the width and height a video model makes, by resolution and aspect ratio, where it bills by them and OpenRouter lists others: Seedance 2.0 makes 864×496 at 480p 16:9, OpenRouter lists 854×480. The values are BytePlus's, as APIYI lists and checked them, and 864×496 is on framy's own bill;
- `clip_min_seconds`: a reference clip is billed as at least this long (Seedance, 3 s);
- `long`: past how many seconds a video model's `long_*` SKUs apply, which their names do not say, and whether the discount leaves them out: HeyGen Video's are "Video Output (over 15 s)" on OpenRouter's page since 2 November, when it went up to 30 s. Up to 15 s HeyGen is priced at its plain rate, exactly. Past 15 s the likely price takes the long rate for the seconds past 15 and the most takes it for the whole video, since no run over 15 s has shown which HeyGen bills; the first such run's actual cost settles it. Without the hint a long SKU stays a maybe, as any SKU with a word the estimate does not know;
- `unlisted`: a line the provider bills that OpenRouter's listing leaves out, at the rate the model's page on OpenRouter gives: FLUX.2 Pro's references at $0.015 a megapixel and Max's at $0.03, by Black Forest Labs' prices, and the prompt, the input pictures and the text and thinking of Nano Banana, which the Images API leaves out and `/api/v1/models` lists. It is added to a route that lists prices but not that line, and the build warns once every route lists it.

`picks_length` is the range of a model that picks its own length. The build warns about a hint that matches no route; every sync logs what the estimate cannot read (`catalog price not understood`), so a new kind of price, or a new GPT Image or Gemini that OpenRouter lists before the overlay does, shows up before someone sees it as "about" or "$?": a price line or a SKU of a shape it does not know, a SKU with a word it does not know and no `variants` entry, a long SKU without `long`, an offer with no price before the run at the settings the composer opens it with (GPT Image 2.6 on 4 November, billed in output tokens with no count of them), and an image offer that takes references and cannot price one. The text and thinking tokens are left out of the last, since no model has a count of them.

Of the video SKUs that fit a run, the most specific wins. When two fit equally, one whose rate is the same as a broader SKU's that fits says nothing of its own qualifier and is left out: Seedance without sound and with a source takes `with_video_input` (its silent rate is the base rate), and Kling with sound takes its sound rate. Two that still differ give the dearer, as "about".

Input images add their own price: per reference at Grok, Seedream Pro, Qwen 3 and K3 Edit, as tokens at OpenAI and Gemini, where the tokens follow the Input detail level, per megapixel at FLUX.2 Pro, Max and Flex. FLUX.2 Klein bills only the output. A clip beside the prompt of Nano Banana is billed in tokens for each second, rounded up. How many text and thinking tokens a Gemini picture takes nobody says before the run, so its price is "about" and leaves them out; the first runs' actual costs settle how much they add. An attached video changes the price too:
- a model that keeps the source's length (`source_video.keeps_length`) is priced by that length, so the estimate is exact;
- a model that takes clips as references (`references.video`, no `source_video`) bills every clip's seconds beside the output's, at the output's rate: Wan 3.0 (job 47 of the shared schema, into which the test bot's jobs moved on 2 November, a run of 30 October 2026 with a 14.948 s clip and 5 s of 480p, $0.848) and HeyGen, whose reference rate then applies to both (job 33, the same clip and length, $0.698); Hailuo 3 as MiniMax bills it. Each clip is rounded up to a hundredth of a second, since the provider measures it itself, and the estimate is "about";
- Seedance switches to its `with_video_input` rate. It bills tokens of 1,024 pixels of a frame at the size it makes (`price.sizes`), 24 frames a second and one more for the output, 24 a second for each clip and at least 3 s of it (`price.clip_min_seconds`), all at the output's size, rounded down to a whole token. Two runs of Seedance 2.0 Mini on 31 October, 4 s of 480p 16:9 with a 2 s clip and with a 3 s one, were billed $0.1485246 each: (97 + 72) × 864×496 / 1024 = 70,726 tokens at $2.1 a million. OpenRouter's pages give the formula without the extra frame and with the listed size. One clip up to 3 s at a size in the table is exact; a longer clip (24 frames a second by APIYI's bills, not framy's), several clips, and a size not in the table (9:21, 4K, Seedance 1.5) are "about". FLUX 3 Video's continuation rate (`video_continuation`) is read but not used while framy sends it no clip; its rates run backwards, 41 cents a second at 720p against 31 at 2K, and get checked before a clip is;
- FLUX Video Upscale bills the video it delivers by the megapixel-second, as Black Forest Labs counts it: the source's size times the factor squared, in megapixels of 1,048,576 pixels, times its seconds, at 24 frames a second and pro rata above. `creativity` picks the rate, 0 Precise and 1 Creative (`price.variants` names the SKUs), and a factor nobody chose is 2, BFL's own default. framy keeps a clip at up to 60 frames a second, so a faster one is priced at 60. The site reads the frame rate of an MP4 or QuickTime clip from its index before Create, the way ffprobe averages it, so the price there is exact too; a clip whose rate is not known (a WebM or MKV before Create) is priced up to 60;
- Aleph 2 costs at least $0.56 a run.

After the run framy records the actual cost:
- OpenRouter: `usage.cost`;
- OpenAI and Gemini: usage tokens times the rates.

A generation keeps `estimate_usd` with the estimate's lines, `actual_usd`, `fx_rate` and `fx_date`. An actual cost more than 20% off the estimate is logged: that is how a price change shows up.

**Currency** **(owner: USD and the person's currency, chosen or by IP)**:
- **Currencies:** USD, UAH, EUR, PLN and BYN.
- **Default on the site and in the Mini App:** the country from `CF-IPCountry` maps to a currency (UA → UAH, BY → BYN, PL → PLN, a country that pays in euro → EUR), otherwise USD. "XX" and Tor's "T1" are no country.
- **In the bot:** it falls back to the language (`uk` → UAH, `be` → BYN, `pl` → PLN), otherwise USD. Russian is spoken in too many countries to say.
- **Choice:** the person changes the currency in the settings; `profile.currency` keeps it, and empty means the default. Auto, the first of the currencies there, goes back to the default and names the currency it gives now, so a pick made by mistake or before a move is undone.

Rates come from the NBU API, UAH per unit, and a cross rate goes through the hryvnia (`internal/fx`). The NBU has no BYN, so BYN always comes from `fawazahmed0/currency-api`, anchored on the NBU's USD of the same day, which makes a price in BYN the USD price times currency-api's rate. BYN is taken only from currency-api's file of that very day, read by date from jsDelivr, then pages.dev. The NBU sets tomorrow's rate at 15:30 Kyiv, while currency-api's file of a day comes out after the day begins in UTC, from a job GitHub often starts hours late (from 05:00 to 06:00 UTC in early November 2026). Until it is out, a price in BYN uses the day before, the newest rate currency-api has, under its own date. currency-api's newest file stands in when the NBU fails, as a warning, not an error; it is read from jsDelivr and from pages.dev and the newer day wins, since jsDelivr's cache can be a day behind. After that the last saved rate stays. A currency-api row never replaces the NBU's for the same day.

The sync asks the NBU only when its saved rates are behind: today's rate from midnight Kyiv, and the next day's from 15:35, five minutes after the NBU sets it. The NBU failing is asked again in 15 minutes, a day it has not published yet in an hour. A price uses the latest rate up to today, so the rate fetched in the afternoon applies from midnight. The NBU's newest day can be days ahead (on Friday afternoon it is Monday's), so every step also reads by date the days missing up to the newest: from the first day kept in the last 31, or from yesterday on a first start, so BYN has a rate before today's file is out. The NBU gives a rate for every day, a weekend's being Friday's, and currency-api keeps a file of every past day. A day with the NBU's rates waits for BYN without a request until its file can be out, half an hour past midnight UTC; then currency-api alone is asked every hour for a day, quietly, and after that at each step, with a warning. So a restart costs no request unless a file is due. A day framy was down for is filled this way, and today's USD, EUR and PLN never fall back to an older rate. `FX_SYNC=off` stops the sync for work without the network.

Amounts are written in the person's language as CLDR writes them, the way the browser writes the site's own numbers (`0,89 ₴`, `$0.02`, `$0,02` in Turkish, `1 234,50 ₴`, and `12.345,50 €` in Spanish, which groups only from five digits), with `zł` and `Br` after the number in every language (`0.077 zł`), and never round down: two decimals from 1 up, and below 1 enough decimals, at most four, for two significant digits. In the composer and the picker a price in another currency has its dollars behind it, and nothing else: not the rate's source, not its day **(owner, 31 October)**. The composer's price, underlined with dots when it has them, shows them on hover, on a tap and on focus from the keyboard, and a screen reader reads them as its description; a price in dollars has no hint and no underline. A job keeps the currency its price was shown in, `fx_rate` as units per USD and `fx_date`.

Whether `CF-IPCountry` reaches the service through the Cloudflare Tunnel is not checked yet; until it is, nothing but this default depends on it.

Not chosen: `gpt-image-2.5-flare` at `low` ($0.0059) and `medium` ($0.0132), since nobody has rated those levels. `meta/muse-image` (1129 for $0.01) is listed on the Images API with no endpoint.
- **Fixed settings:** the image model at about 1K with one result; the video model at 5 s and 768p, with an optional start frame and no references. Other controls are locked with "with your key". The server holds the same line: a free job on another model, with another setting or with more files than the model takes is refused before anything is created.
- **Video edit (owner, 27 October):** the weekly video can instead be an edit of a clip up to 5 s on `flux-video-edit`, $0.15, cheaper than the generated one. Either one uses up the week. A longer clip gets the same two ways out as above **(owner)**: pick 5 s of it, or pick a model that takes more, which runs on the person's own key. The queue checks the length framy read when it kept the clip, in the transaction that admits the run: a clip over 5 s, a picture in its place and a clip of unknown length are refused. A 5 s part cut from a longer clip measures a frame more (5.033 s at 30 fps), so up to 0.1 s over goes.
- **Payer:** framy's own OpenRouter key (`OPENROUTER_API_KEY`, or a file through `OPENROUTER_API_KEY_FILE`): one bill, no OpenAI limit of 20 images a minute. Without it a free run fails as `key` before anything is paid.
- **Where it is checked.** The jobs queue asks `internal/free` inside the transaction that creates or queues a free job, under a lock per person and then one for the budget, so two requests at once cannot both take the last slot or the last cents. A draft takes no slot until "Create", which checks again.
- **What counts.** By the time the run was queued. A run takes a slot while it is queued or running, when it is done, and when the provider refused it for its content (`moderation`), so probing costs something. A run that failed otherwise, including one refused for a setting, was cancelled or expired takes nothing. A repeated request is the same run, not a second.
- **Two fuses:**
  - **The day's budget (owner, 27 October):** $1 a day, about 50 free images (`FREE_DAILY_BUDGET_USD`). A run is refused when what the day's free runs have cost, plus its own estimate, would pass it, and the tier stays closed until 00:00 UTC with a plain message. A run costs its estimate while it is queued or running and what the provider charged once it ended. One that may have been paid and has no cost on the books (done with none reported, expired, or failed as a timeout, an interruption, an unreadable answer, results that could not be kept after the request went out, or a refusal for its content after the provider took the run and gave it an id) keeps its estimate. A refusal before the provider took the run costs only what the provider reported. Of an "up to" estimate the budget and the key's fuse count the top (`max_usd`), since that is what the run may cost.
  - **The limit on framy's OpenRouter key.** The owner sets a daily limit on the key in OpenRouter. framy reads `GET /api/v1/key` every minute and closes the tier when `limit_remaining`, less the free runs still on their way, cannot pay for the run: until 00:00 UTC for a daily limit, until the limit is raised for any other. A free run that fails as `money` closes it for 15 minutes too, which also covers an account out of credit. A reading older than five minutes is ignored, since OpenRouter's own refusal still stops a run.

  The operator chat (`OPERATOR_CHAT_ID`) is told the first time each fuse closes the tier on a UTC day, and a notice that failed is tried again by the next refusal. A refusal is a typed error that carries which limit, when a slot frees up or until when the tier is closed, and the surfaces word it. The site names the time of the next free run in the browser's time zone, with the date when it is not today, both on a refusal and under Create; the settings keep how long until it. Once the allowance cannot pay a model it would (used up, or paused), the run goes on the person's key and the price is its price there, not "Free". With no key that works, the button connects OpenRouter, whose key pays the free runs, instead of standing grey (in the Mini App the main button does), and when free runs are back stays under the price; on a phone a button that long takes a line of its own, so that line reads to its end. Free is then no choice in Pay with, and Free chosen earlier, or kept by a run brought back to the composer, gives way until it can pay again. A free run's refusal or failure offers the run on the person's key, or the connect when no key works. The line under the price is never cut: on a phone it runs under the button across the dock, and it wraps where it is still too long.

## Jobs

Everything is a job in Postgres:

```text
draft ──Create────> queued ──> running ──> done
  │                   │           ├──────> failed
  └──No / 10 min──> cancelled     └──────> expired
```

`draft` exists only for a chat preview waiting for "Create".

**API** (`internal/api`). `POST /api/jobs` answers 202 with the job at once, and the client follows `/api/jobs/{id}/events` over SSE, with polling as the fallback. Cloudflare answers 524 when the origin sends nothing for 125 seconds, and an OpenAI image can take two minutes, so no request waits for a generation. The person comes from the sign-in (`Config.Person`, which is `Auth.Identify`); nobody gets 401 `{"error":"sign_in"}`, and a request whose session could not be read gets 503 `{"error":"unavailable"}` with `Retry-After`, so a moment's outage of the database signs nobody out. The site that could not read the person at start asks again after 3, 10 and 30 seconds. Errors are `{"error": code, "message": …}` plus fields of their own.
- `GET /api/catalog`, for anyone: every model that is on and shown, with its traits (effort, references, source video, a length the model picks, continuation, faces), its place in the picker (`family` with its name, rank, `default` and `outdated_by`; `fast_of` and `fast`), its note in the person's language (core's where framy speaks it, else the first language of `Accept-Language` framy speaks, as for amounts), `deprecated`, `shuts_down` and `successor` where the maker said the model goes away, its offers with their parameters, their `defaults`, their `inputs`, `expires_on`, the discount when every route has the same one and `typical_seconds` (the wait, under Video), the suggestions by situation (`recommend`), and the free allowance: the window of each kind and every free model with its locked settings, `start_frame` for a video from a start frame and `max_source_seconds` for an edit of a clip (5 for FLUX Video Edit). The price hints stay on the server. The API keeps the catalog in memory for a minute.
- `POST /api/quote`, for anyone: `{items: [{offer, pay, prompt, settings, inputs, files, continues}], batch}`, up to 200 runs at once, each with its own offer and payer. `files` are what the browser read of the files it still holds (`content_type`, `bytes`, `width`, `height`, `seconds`, `fps`); a photo is priced at the size the upload pipeline will give it, 2048 px on the long side at most. Each item comes back with the estimate as `POST /api/jobs` keeps it (the same `price.Of`), the settings the run would go with (the allowance's locked values on a free run, the defaults on a key, the shape following the first file), and, for a signed-in person who named a payer, the refusal `POST /api/jobs` would give now, with its status: no connection, the free limit with `frees_at`, the tier closed, not a free model, a file that is not theirs, a job that cannot be continued. The settings it gives back never carry the provider's job id of a continued run. An offer that is not offered comes back as `unknown_offer` among the others, a setting the offer does not have as `unknown_setting`, and files the offer does not take as `wrong_inputs`, to anyone; each is still priced. With `batch: true` the items are the frames of one press: the answer adds `jobs`, the items that would go as one job by their place (`[[0,1,2,3],[4]]`), and `total`, the price of the items not on the free allowance summed (`price.Sum`: the figures add up, the kind is the least sure of theirs), absent when every item is free. The page keeps the latest 1000 answers of the quote (the ones on screen are read again with every batch and stay), and a quote that did not come because the network was down or the server busy (no connection, 429, 5xx) is asked again after 2, 4, 8 and 15 s, up to five times, so a price shown as "…" fills in by itself; a refusal of the request is not repeated. An item of unknown price adds nothing, and the total is `from` the sum of the others, the least the press costs; it is `unknown` only when every item is.
- `GET /api/me`: `{user_id, name, photo_url, language, language_chosen, currency, currency_chosen, currency_auto, signed_in_at, connections, default_models, deliver_to_telegram, free, storage}`. `name` and `photo_url` are empty for a person who has not signed in since names were kept; `language_chosen` is true only when the language is the person's own pick in framy (`profile.language_picked`, set with core's claim, since framy may call core's language functions but not read whose claim won), so false is "Automatic" even when another bot of the family has a pick. `currency` follows the rules of the estimate below, `currency_chosen` is true only when it is the person's own pick, and `currency_auto` is the one the rules give without a pick (what Auto in the settings gives). `connections` are the person's keys (`id`, `provider`, `last4`, `status`, the last success and the last error's class), never the key, each with `spent` and `spent_30d`: what framy's paid runs on that provider cost by the provider's bill since the key was saved, and of those the last 30 days, as `{usd, amount, currency, label}` in the person's currency at today's rate. A replaced key starts from zero, a run whose bill is not known yet is not in them, and neither are runs made with the key outside framy. `default_models` is `{image, video}`, the model id the composer opens on for each kind, and the chat's preview too where the run can go on it (`/img` and `/edit` in a group, step 3), a kind without one left out; a model may since have left the catalog, and the composer then opens on its own default. `deliver_to_telegram` says whether results made on the site go to the DM. `free` is each kind's `used`, `limit`, `left`, `window_seconds` and, while none is left, `frees_at`. `storage` is how many files framy keeps for the person and their `bytes`, absent when framy keeps no files.
- `PATCH /api/me`: `{currency, language, default_models: {image, video}, deliver_to_telegram}`, any left out to keep it. An empty one goes back to the default: the currency of the country or the language, the language core resolves from the family's bots or from Telegram, and the composer's own model. The language is the family's, kept in core for every bot, as picking it in any of them does. A default model is an id of `GET /api/catalog` of that kind, shown and on; any other is refused with 400 and `field` `default_models.image` or `default_models.video`. Every field is checked before any is kept, so a refused request changes nothing, and they are kept in one transaction, so a save that fails half way changes nothing either. The answer is `GET /api/me` as it is after.
- `PUT /api/connections/{provider}` with `{"key": …}`, `DELETE /api/connections/{provider}` and `POST /api/connections/{provider}/check`, for `openai`, `gemini` and `openrouter`: saving checks the key and keeps it in place of the person's earlier key of that provider (see Providers and keys), the check is "Re-check", and each answers with the connection as `GET /api/me` lists it; a delete answers 204. A key is never in an answer, an error or a log, beyond its last four characters.
- `POST /api/uploads`: the photo as the raw body, one per request, 201 `{id, content_type, bytes, width, height}`. The body comes in whole, to a working file, before the photo waits for one of the 4 conversions that run at once: a phone on a slow line keeps no one else's photo waiting. A photo whose bytes are in waits up to 20 s for a conversion, then gets 503 `busy`. At most 2 photos of one person's come in at once, as from two tabs; a third gets 503 `busy`. The upload route has longer deadlines than the rest.
- `POST /api/videos/uploads`: `{bytes}`, the size of the clip or sound about to go up, and the answer is where to put it, 201 `{token, url, expires_at, max_bytes, max_seconds}`. `url` takes a presigned PUT of exactly that many bytes, for 10 minutes; a size over 512 MiB gets 413 `too_large` with `max_bytes` and no link, and a request without a size 400 with `field` `bytes`. A clip does not come through the service, since Cloudflare takes at most 100 MB in a request. The link is a secret and is never logged.
- `POST /api/videos`: `{upload}` takes the clip or sound put under that token, `{file}` cuts one framy keeps already, and `start` with `seconds` picks a part, which a `file` needs. It answers 202 `{task, status: "processing"}` with `Location`, since reading and encoding a clip can outlast the 100 s Cloudflare waits. The same request while its task runs, or after it went well, gets that task; after a failure it starts a new one. Two clips are worked on at once, and at most 16 may run or wait, 3 of them one person's, else 503 `busy`, which the site waits out with a countdown. A task may take 10 minutes. The limits follow the machine's ffmpeg, not the traffic, and every busy answer is counted (`framy_busy_total`, under Metrics).
- `GET /api/videos/{task}`: 200 with `status: "processing"`, then 200 `done` with the `file` (`id`, `content_type`, `bytes`, `width`, `height`, `seconds`, `fps`, `audio`; a sound has no picture size and no frame rate, and `audio` true), or the error the clip ran into, with its status, `task` and `status: "failed"`. Tasks live in memory and are kept 15 minutes after they end. After a restart the client starts again from the clip, which stays in `incoming/` until it is taken, a day at most.
- `POST /api/files/{id}/last-frame`: the last frame of a clip of the person's, kept as a photo, 201 as `POST /api/uploads` answers. It reads the last second only, so it is answered at once. The photo remembers the clip and where in it the frame is (`frame_of`, `frame_at`, migration 026), so the run that starts from it is joined to the clip. A client continues from a job's joined clip when it has one, so each Continue adds to the whole.
- `POST /api/files/{id}/share`: Send to Telegram of a result of the person's from a job that is done (see Mini App): 200 `{id, expires_at}`, the prepared message for `shareMessage`. Another file is a 404. Without the bot it is 503 `telegram_unavailable`, and 502 `telegram_unavailable` when Telegram refused to save it.
- `POST /api/jobs`: `{offer, prompt, settings, inputs, pay: "free"|"key", shown_usd}` and a required `Idempotency-Key` header, which with the person is the job's `dedupe_key`: a repeat answers the same job with `Idempotent-Replayed: true`, or 404 when that job was deleted since. The answer is the job (as `GET` gives it) with an `estimate` quoted in the person's currency: their own choice, else the country Cloudflare saw (believed only through the trusted proxy), else the language, else USD. The rate used is kept on the job. `shown_usd` is the price the person saw, the figure of the quote's label: a run on their key whose price would now show higher in their currency is refused with 409 `price_changed` and the new estimate, and waits for another press; a lower price, or one the label rounds to the same amount, runs. A run on a key needs it: one without it is refused the same way, since the person saw no price, unless framy cannot price the run either (`unknown`). A free run needs none. `continues` is a finished job of the person's whose video the run goes on from (see Actions on a result). A free run from a start frame gets `frame_images` from the allowance, and a run with pictures on a video model that takes no reference images gets them as its frames, first then last, when it does not say; a setting may be a short list of texts, as `frame_images` is. A setting the offer does not have is refused with 422 `unknown_setting` and its name before a job exists: one of the offer's parameters, one of a route's on OpenRouter's Images API, and `frame_images` on a video are settings, and one sent as `null` is none.
- `POST /api/batches`: the frames of one press, `{prompt, inputs, surface, shown_usd, frames: [{offer, pay, settings, prompt?, inputs?, continues}]}` with one `Idempotency-Key`. A frame's own `prompt` and `inputs` replace the press's; a frame carries no `n`, since framy sets it (Frames). Each frame is checked as `POST /api/jobs` checks a run, and a refusal names it in `frame`; pictures and videos do not mix. The jobs are queued in one transaction, all or none, so a free limit met by the third frame starts nothing. `shown_usd` is the sum of the frames that are not free, needed when there is one, as the quote's `total` gives it: a frame of unknown price leaves the others' sum checked, so one frame nobody can price does not let a rise in the rest go unasked. The answer is 202 `{batch, jobs}`, each job as `GET` gives it with `batch` and `frames`, the frame of each result in order; a repeat answers the same jobs with `Idempotent-Replayed: true`. It counts once in the jobs' rate limit, and a person's jobs still run two at a time, videos out at the provider aside (Limits).
- `GET /api/jobs/{id}`: status, a message fit to show when it failed, the estimate, the actual cost, what was asked (`model`, `prompt`, `settings`, `surface`) and links to the inputs and the results, a video result with its `seconds`. A result also has `download`, a link like `url`, made at the same time and good as long, whose answer saves the file as `framy-<job>-<n>.<ext>` (`response-content-disposition: attachment`), n counting the job's results from 1: the site uses it as a plain link and the Mini App passes it to `Telegram.WebApp.downloadFile`. An input has none. A result has `thumb: {url, width, height}` once its thumbnail is made, for the library's grid; without it the client shows the file. A run Continue started from a clip's last frame has `joined`, the clip with the run's video after it, as one file with its own `url`, `download` (`framy-<job>-joined.mp4`) and `thumb`, and `segments`, where each part begins in seconds, the first at 0 (absent for a clip joined before migration 027); the run's own video stays in `results`. Every link is the same for the hour (Storage and retention, Serving). A job of someone else, or one deleted, is a 404 on every route.
- `GET /api/jobs`: the history, the person's jobs that were queued, newest first, each as `GET /api/jobs/{id}` gives it, as `{jobs, next}`. `kind` is `image` or `video`, `q` a part of the prompt in any case (up to 200 characters; `%` and `_` are only themselves), `failed=1` only the jobs that ended without a result (failed, cancelled or expired), `before` the `next` of the previous page, `limit` 1 to 100 (30 by default). A draft never generated and a deleted job are not in it. A page ends where a batch does: one that would cut a press takes the rest of its jobs. The links of a page are signed at once, in one read of the rows.
- `DELETE /api/jobs/{id}`: the job's results go, with the uploads no other job of the person's takes, and the job leaves the history; 204. A job that has not ended is refused with 409 `job_active`. See Storage and retention.
- `POST /api/jobs/{id}/cancel`: a queued job is cancelled and comes back as `GET` gives it. A running one is refused with 409 `job_running`, since a provider cannot be stopped half way, and a draft with 409 `job_draft`, since its preview in the chat answers it. A job that ended comes back as it is.
- `DELETE /api/me` with `{"confirm": true}`: the account goes (see Storage and retention); 204. While a job is queued or running it is refused with 409 `jobs_active`.
- Refusals: `free_limit` 429 (with `frees_at`), `free_closed` 503 (with `until`), `not_free` 422, `no_connection` and `connection_invalid` 402, `unknown_offer` and `unknown_input` 422, `unknown_setting` 422 (with the `setting`), `wrong_inputs` 422 (with the offer's `inputs`), `price_changed` 409 (with `estimate`), `key_in_prompt` 422 (with the `field` and the `provider` the key looks like it is for: the prompt holds something shaped like a key, see Keys in chat; a quote is not refused), `bad_request` 400 (with the `field`), `too_many_streams` 429, `job_active`, `job_running`, `job_draft` and `jobs_active` 409, `storage_unavailable` 503. A key's: `unknown_provider` 404, `bad_key`, `key_rejected` and `key_forbidden` 422, `key_unreadable` 409, `key_in_use` 409 when a video sent with the key is still being made, `check_unavailable` 503 with `Retry-After`, `keys_off` 503 when the server keeps no keys, each with the `provider`. A clip's: `cannot_continue` 422 (with `continues`), `no_upload` 404, `not_a_video` 422, `video_too_long` 422 (with `seconds` and `max_seconds`), `bad_cut` 422, `unreadable` 422, `unsupported_type` 415, `too_large` and `frame_too_large` 413, `busy` 503, and `wrong_inputs` 422 (with the `input`) for a kept clip of unknown length, which is cut once to get one. A share's: `not_shareable` 422, `telegram_unavailable` 502 or 503.

**SSE through the Tunnel.** cloudflared flushes every write for `text/event-stream`, and Cloudflare does not compress it. The handler:
- sends the headers at once (`Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`);
- flushes after every event through `http.NewResponseController`;
- writes a `: ping` comment every 15–20 s;
- has no `WriteTimeout` on this route: `web.Stream()` removes the read and write deadlines, and the handler sets a write deadline of its own before each write, so a client that stops reading cannot hold it;
- resumes from `Last-Event-ID`;
- asks the sign-in again at every wake and ping, so signing out, here or everywhere, or a Mini App token running out ends the stream within a ping (sign-in remembers a session for 30 s at most, and forgets it at once when it ends in this process). The reconnect gets 401, and the page forgets the person and the run with them. A lookup that failed keeps the stream.

Every event is `id: <n>`, `event: job` and the whole job as `data`, as `GET /api/jobs/{id}` gives it. `n` is the job's `event_seq` (migration 009), which grows with every change a person can see, so a stream that reconnects gets only what is newer than its id, and one that comes back to a finished job it has seen to the end gets 204, which stops `EventSource`. The first event is the state now; the stream ends after the final one. What the provider charged for a finished run is an event of its own, while the job is still `running`: it is written before the results are copied (see Paid requests). A burst of changes may arrive as one event: each is the whole state, never a difference. At most 3 streams per person; the 4th gets 429 `too_many_streams`. `EventSource` cannot send an `Authorization` header, so the Mini App streams with `fetch`.

The client (`watchJob` in `api.js`) reads the job every 5 seconds instead of streaming after a 429, and after a stream that keeps failing: a 5xx of framy's or of the tunnel's is tried again after a pause that grows (or the `Retry-After`), the page says it lost the connection from the second one, and the fourth gives way to reading. A stream that has said nothing for 45 seconds, three pings, is a connection that died without a word and is opened again. A 404 ends the watch, the run leaves the stage and the page says there is no such run in the library (the job is not the signed-in person's); a 401 ends it too, and the run stays, saying it goes on on the server while nobody is signed in; signing in from there comes back to it as `/r/<id>`, where the library goes on following it.

**Queue.** River OSS (v0.49.0, MPL-2.0) in the `framy` schema, in `internal/jobs`. A job is a row in `framy.job`, which the surfaces read, and a River job that works it, inserted in one transaction (`InsertTx`). River's migrations run at start under framy's migration lock, since they take none of their own. River's listener needs a real Postgres session, not PgBouncer in transaction mode.
- Queues with their own `MaxWorkers` per process: `openai` 4, `gemini` 4, `openrouter_image` 8, `openrouter_video` 4. `ffmpeg` and `telegram_send` come with their features.
- A repeated update starts nothing: a job keeps a unique `dedupe_key` (`tg:<update_id>`, or the request's key on the site), and "Create" queues a draft once.
- A background run waits snoozed (`JobSnooze`), which spends no attempt and holds no worker. It is asked every 30 s and expires after an hour, as `timeout` whatever the last poll met: the request went out, so the run may be paid, and a class that says nobody answered would show nothing charged. A poll that fails can carry the cost beside its error, and the expired run keeps it. A video the provider finished and framy could not fetch by then (`Outcome.Ready`) ends instead as `storage`, failed with its cost: it was made and billed, and the person reads that it came out but was not saved, not that the model took over an hour. When the provider asks to wait, the next question waits that long, up to 10 minutes and never past the hour.
- River rescues a job whose worker died after 5 minutes, or after the job's own limit when that is longer: River leaves a job alone until it has passed. An image's attempt may take 7 minutes (the worker's `Timeout`): the call gets 180 s, the writes that follow it 30 s, and copying its pictures to R2 gets 30 s and 2 s for each MiB of them, up to 2 minutes, so that four 4K pictures over the host's line are not cut short. A video's attempt may take 10 (marked by `video` in the River job's args): the poll that finds it done downloads it in the same call, which gets 5 minutes, and copying it to R2 gets 3 more. The write that ends the job gets 30 s of its own after the copy, however long the copy took, so a paid result kept late is still done, and one that could not be kept fails as `storage` with its cost. Each attempt has a minute to spare beyond the sum of these, so River never rescues one still at work.
- An error of framy's own, such as the database or the bucket not answering, is tried again by River up to 5 attempts in all. After the last one the job fails by what is known of the money: `storage` for a finished run whose results could not be kept (the provider still holds a video's, so each attempt asks for it again), `interrupted` once the paid request went out, and `internal` only when nothing was sent. The cost written down so far stays on the job.
- A sweep every minute cancels drafts left unchanged for 10 minutes and fails a job River gave up on without working it. A draft's 10 minutes count from its last change (`updated_at`), so a person still choosing the model or the settings on the preview's panels is not timed out by its age. A draft that ended without running is cleared within the hour after (Storage and retention).

Progress for SSE goes through `pg_notify('framy_events', …)` in the transaction that changes the state, with one listener per process. The same connection listens on `framy_sessions` (Accounts). Triggers on `framy.job` do both the numbering and the notice, so every path that changes a job is covered and a rollback announces nothing. The payload is only `{job, seq}` (migration 033; until then it also named the person and the status): any role connected to the shared database may LISTEN, since LISTEN asks for no rights, so a notice names nobody. A stream rereads its job when woken. The listener holds its own connection, reconnects with a growing delay and wakes every stream after each connection, and a stream rereads on its ping, so a lost notice delays an event and never drops it.

**Workers.**
- **Images:** one provider call inside the worker, with a 180 s timeout.
- **Memory.** The container has 1 GiB, and the process holds the Go heap to three quarters of what its cgroup allows (`memory.max`; `GOMEMLIMIT` wins when set), so the collector frees the garbage of large answers before the kernel kills the process, with the bot and the site; FFmpeg has the rest. An answer of OpenAI or OpenRouter carries its pictures in base64, up to 256 MiB, and is read one picture at a time, decoded straight into bytes (`internal/providers/answer`): it takes about its decoded size, three quarters of the answer, where reading it whole took three times the answer. A Gemini answer is read whole into one buffer of its length, since its reasons are read from it again, and with its pictures decoded takes about 1.75 times its size. These limits bound one answer, not all of them: every worker of every queue holding an answer at its limit at once would need about 4 GiB, while a 4K PNG is 10 to 30 MB. What is left to weigh against that is `mem_limit` in the compose files and the workers of each queue.
- **Video:**
  - submit, then poll. OpenRouter `GET /api/v1/videos/{id}` every 30 s; Omni with `background: true` and `GET /interactions/{id}` (see "Gemini video").
  - The submit gets 60 s, and 3 s more for each MiB of the run's files, up to 5 minutes (`callLimit`): Omni's request carries them inline, so a 48 MiB clip is downloaded from R2 and sent as some 64 MiB of base64 within the call, which over the host's line takes minutes. The 3 s are the download and the upload at the 2 s a MiB the copy to R2 assumes; the line itself has not been measured.
  - A finished video is held in memory while it is copied, so it may be at most 128 MiB: four workers hold 512 MiB at most, and a 10 s 1080p clip is 10 to 30 MB. A larger one fails the run as `storage`, after it was paid.
  - The provider job id is written to the database right after the paid submit, before any polling. Otherwise a retry after a crash pays for the video twice. If the id cannot be saved, the retry fails the job as `interrupted` and sends nothing, and the log has the id.
  - A poll ends the run only on an answer about it. A key refused, or a balance short, is trouble with the asking: the run was sent and is likely paid, so the poll asks again every 30 s until the hour is up, and a key put right fetches the video. Past the hour the run expires with that class; the site says the provider may have charged for it, and the chat card says what is wrong with the key.
  - An OpenRouter video request carries a `callback_url` with a path nobody can guess, `/hooks/or/<job>/<mac>`, when `HOOK_PATH_SECRET` and an https `SITE_URL` are set (see "OpenRouter video"). Without them the poll alone finishes every video.
    - **framy's own key:** the `X-OpenRouter-Signature` check, an HMAC-SHA256 of `t + "," + raw body` with a 300 s window.
    - **A person's key:** the workspace secret belongs to the person, so the webhook is only a signal, and framy rereads the status with that key.
  - Webhooks are deduplicated by `X-OpenRouter-Idempotency-Key`. Polling every 30 s stays as the fallback. `callback_url` works with OAuth keys too (open check 10).
- **Inputs.** A job's files are found just before the paid request (`jobs.Inputs`), as links the provider can fetch, made anew for each submit: presigned R2 URLs, or data URLs. A picture's provider fetches them during its call, and their links live 15 minutes. A video's takes the run and may start it, and fetch the frames and references, only when its own queue lets it, so their links live 65 minutes: as long as framy waits for the run, with a margin for the clocks. A job takes only its owner's files, written to `job_input` in the transaction that creates it. A file deleted before the run fails the job as `storage` before anything is paid; storage that does not answer is asked again. A presigned link a provider echoes in its error is taken out before the error is stored or logged.

**A run the adapter does not send.** Every adapter checks the run against the offer before the paid call: a setting the offer lacks, a value outside the catalog's, an empty prompt, files the model does not take. Such a run fails as `invalid_request`, with framy's own words as its message, and nothing reaches the provider or is paid. `refused` is kept for the provider's own answer, which the tables below list.

**OpenRouter images** (`internal/providers/openrouter`). `POST /api/v1/images` answers with the image in base64, so a run is one call:
- the model is the offer's OpenRouter id. Settings go as fields of the request, and pass-through ones go under `provider.options.<route>`. OpenRouter lists `seed` and `size` as booleans, meaning only that a route takes them; their values are a whole number and a size;
- references go in `input_references` as `image_url`. A video is refused, since the Images API takes only images;
- `provider.sort` is `price`, so the cheapest route goes first, as the estimate assumes, and OpenRouter may fall back to another. When only some routes take the settings or the number of references, `provider.only` names them. A run that no route takes, a value outside the catalog's or an empty prompt is refused before the call, so it costs nothing;
- `user` is a hash of the person's id (`jobs.SafetyID`), never the id itself. It is a plain SHA-256, so it hides the id from a casual reader, not from someone who tries every Telegram id;
- every request to OpenRouter, image or video, names framy in its app attribution: `HTTP-Referer` is `https://t.me/framyin_bot` from every stack **(owner)**, `X-OpenRouter-Title` is `framy`, sent also as `X-Title`, the older name OpenRouter still takes, and `X-OpenRouter-Categories` is `image-gen,video-gen`, two being the most a request may name;
- the actual cost is `usage.cost`. When the person's OpenRouter account runs the model with its own key of the provider behind it (BYOK, `usage.is_byok`), that is only OpenRouter's fee and the provider bills the run itself: the cost is then the fee and `usage.cost_details.upstream_inference_cost`, the provider's bill, together, and unknown when OpenRouter does not give the bill, since the fee alone is a small part of what was spent. OpenRouter documents that bill for BYOK runs only, so outside BYOK the field (null, 0 or the charge again) is not added. An error inside a 200 is read as well: it arrives when the provider had taken the request, so it is never retried, and its cost is kept when the answer has one.

| OpenRouter's answer | Class | Retried |
|:--|:--|:--|
| 403 with `metadata.reasons` or `flagged_input`, or `error_type` `content_policy_violation` or `refusal` | `moderation` | no |
| 402; a 403 whose `limit_source` is a budget or the key's limit | `money` | no; a 402 for the in-flight budget with `Retry-After` waits that long and goes again |
| 401; any other 403, such as a guardrail on the model | `key` | no |
| 400 that passes on a provider's refusal of a real person in an input (`Input…SensitiveContentDetected.PrivacyInformation`, BytePlus for Seedance) | `faces` | no |
| a refusal of the sound the model made ("the output audio may be related to copyright restrictions", BytePlus for Seedance) | `sound` | no |
| 400, 404, 413, 422, image errors such as `image_download_failed` | `refused` | no |
| 429 | `rate_limited` | after `Retry-After`, up to 10 minutes; a longer wait ends the run |
| 503, 529, a connection that was never made; Cloudflare's 521, 522, 523, 525 and 526, a request it could not hand to OpenRouter; an image's 502, a generation that did not complete | `unavailable` | after `Retry-After` or 5 s × requests², up to 10 minutes; an image's 502 three requests in all |
| 408, 504, Cloudflare's 524 | `timeout` | no: the run may go on and be paid |
| 500, Cloudflare's 520; 502 other than an image's (`provider_unavailable`, the provider's empty or broken answer); an answer that cannot be read | `provider` | no: the request reached the provider |

The moderation's reasons and the provider's name go into the job's error; the flagged text itself does not. OpenRouter passes on the answer of the provider behind it as its message, `HTTP 400: {"error": {"code", "message"}}`: framy reads the provider's code and words out of it and drops the request id at their end. The code goes into the job's error for the logs. The words, the provider's own as every adapter has them (`Said`), are kept apart in `job.provider_message` (migration 023), whether the request failed or the run ended without a result (a refusal inside a 200, a failed video), and the API gives them as `error.message` in place of framy's whole line, with `error.from_provider`: "The request failed because the input video 'content[1]' may contain real person." A run framy did not send, or an answer with no words of the provider's (a proxy's page for a 502, whose status's name is framy's, or a failed video with no reason), keeps framy's line without `from_provider`, and the site shows a message as the provider's only with it. Gemini's are Google's explanation of a block, or the model's own words when it answered in text instead of drawing. OpenRouter's documentation calls a 502 (`provider_unavailable`) an empty or broken answer of the provider: the request reached it, and whether a video or a call of another adapter that ended in a 502 is ever billed is not checked, so it is not sent again, and the free budget counts it as paid. Its image guide says what a 502 of the Images API is: "When a generation does not complete, the request returns a 502 Bad Gateway", and "a generation is either completed and billed in full, or it fails and is not billed". OpenRouter may have tried the model's other routes by then, and each try is a whole generation, so an image's 502 goes again at most twice (`jobs.Error.Tries`), three requests in all instead of the queue's five; a model that failed on a prompt three times seldom makes it on the fourth, and the person has waited long enough.

**OpenRouter video** (`internal/providers/openrouter`, `video.go` and `hook.go`). `POST /api/v1/videos` answers 202 with a job id. The settings go as fields of the request and are checked against the offer's parameters before anything is paid:
- a file is a frame or a reference. The `frame_images` setting lists the frame type of each of the job's first files (`["first_frame"]`, `["first_frame", "last_frame"]`), and the other files go in `input_references` as `image_url`, `video_url` or `audio_url`. OpenRouter keeps the frames and drops the references when both come, so a run with both is refused. The free plans of a video from a start frame (`internal/free`) set `frame_images` themselves, since a photo sent as a reference is priced apart: HeyGen's 768p is $0.10 a second that way and $0.036 as a start frame;
- `size` replaces `resolution` and `aspect_ratio`. A pass-through setting such as a negative prompt goes under `provider.options.<tag>`, the tag of the model's one upstream, which the hourly sync reads from `/models/{id}/endpoints` (`google-vertex` for Veo, `atlas-cloud` for Kling and Wan); Veo's go one level down, in `parameters`, as OpenRouter documents for Veo alone. A blank one is not sent, and a model whose upstream is unknown or not alone refuses it before anything is paid. No `user` is sent: the Videos API documents none;
- `completed` is the downloaded results with their cost, read as for an image (BYOK included); `failed` is `sound` when the provider refused the sound the model made (Seedance 2.0 Mini with sound on, 31 October: no usage, and the same run without sound went through), `moderation` when its text names a content filter and `provider` otherwise; `cancelled` is `provider` and `expired` is `timeout`. A status framy does not know is a run still going, and the hour's deadline ends it. A GET that answers 404 or 400 says nothing about a run that may be paid and finishing, so it is asked again;
- results come from `/videos/{id}/content?index=N` with the key, never from the URLs in the job object: unsigned ones need a key that must go only to OpenRouter, and signed ones are secrets. The download goes through `safehttp`, the key is dropped on a redirect to another host, and a link never reaches an error. A video above `MaxResponse` ends the run as `storage` with its cost kept. The run is paid by then, so a download that fails otherwise (a wait, OpenRouter down or slow, a 404 of a copy still on its way, an answer cut short) is asked for again at the next poll until the hour's deadline, which ends the run as `storage` with its cost; only a key that stopped working, money or a filter ends it sooner, with its cost too.

The webhook, `POST /hooks/or/{job}/{mac}`, checks in this order:
1. the MAC in the path: base64url HMAC-SHA256 of the job id under `HOOK_PATH_SECRET`, compared in constant time before anything is read. A wrong one is a 404 and the path is not logged;
2. for a free job, when `OPENROUTER_WEBHOOK_SECRET` is set: `X-OpenRouter-Signature`, `t=<unix>,v1=<hex>`, over `t + "," + raw body`, within 300 s either way. The format is taken from OpenRouter's documents and has not been seen live (`live_video_test.go` checks it). Without the secret a free job's webhook is a signal like a person's;
3. the delivery's keys, SHA-256 digests of `X-OpenRouter-Idempotency-Key` and of the signature, go into `webhook_delivery` in the transaction that brings the poll forward (`jobs.Queue.PollNowTx`, River's `JobRetryTx`), so a retry or a replay within the window does nothing twice;
4. the answer is a 204 for everything but a wrong path (404), a bad signature (401), a body above 64 KiB (413) and framy's own failures (500, which OpenRouter retries). The request does no work of its own.

A webhook that lands while the job is being polled brings nothing forward: River does not touch a running job, and the poll's own turn comes within 30 s.

**OpenAI images** (`internal/providers/openai`). A person's own key pays, never framy's: the adapter takes its key from `keys.Service.JobKey`, which refuses a free run, and what an answer proves about the key (`APIError.KeyStatus`: a 401 is `invalid`, a 403 that asks for verification `needs_verification`) becomes the connection's status. A run is one call:
- without references `POST /v1/images/generations`; with references `POST /v1/images/edits` with a JSON body, each reference an `images[].image_url`: the presigned R2 link, which OpenAI fetches, or a data URL. An upload is PNG or JPEG with the long side at most 2048 px and a result is what its model made, up to a 4K PNG, both inside OpenAI's 50 MB and 16 images; a type OpenAI does not take is refused;
- `quality` is always one of the offer's levels, `low` to `max`. `auto` and no quality at all are refused before the call, since OpenAI would choose how much to spend. `size` is always `WxH` within OpenAI's rules (sides in multiples of 16, a side up to 3840, a ratio up to 3:1, 655,360 to 8,294,400 pixels): any such size goes, not only the catalog's list, which is what the composer draws. A run with no size goes at 1024×1024, the size the estimate assumes. Other settings go as fields when the offer lists them and allows the value. `moderation` stays at OpenAI's default, `auto`;
- `safety_identifier` is `jobs.SafetyID`, the same hash as OpenRouter's `user`: SHA-256 of `framy:` and the Telegram id, the first 16 bytes in hex. OpenAI asks for a stable identifier per person, so that an abusive person is told apart from the key's owner and the whole key is not blocked; the hash gives it without handing over the Telegram id. Being a plain hash of a small number it hides the id from a casual reader, not from someone who tries every id;
- the actual cost is the answer's usage tokens times the offer's own rates: text input, image input (the references) and image output tokens, the lines the estimate is made from. The text a model writes (`output_tokens_details.text_tokens`) goes at the offer's `output_text` rate where it lists one; OpenAI lists none for GPT Image 2 and later, so there it counts at the image's. Tokens the usage does not split are priced at the dearer rate of their side, so the cost is never below the bill. A refusal or a failure inside a 200 keeps the cost when the answer has a usage.

| OpenAI's answer | Class | Retried |
|:--|:--|:--|
| `moderation_blocked`, with `moderation_stage` (`input`, `output`) and the categories when OpenAI gives them | `moderation` | no |
| a code or type of credit or a limit: `insufficient_quota`, `credit_balance_exhausted`, `billing_hard_limit_reached`, `organization_spend_limit_exceeded`, `project_spend_limit_exceeded`, `organization_usage_limit_exceeded` | `money` | no |
| 401; 403, such as a project without the model or an organization that is not verified; 404 `model_not_found` | `key` | no |
| 403 `unsupported_country_region_territory`: framy's server is where OpenAI does not serve | `region` | no |
| other 4xx, such as a setting or a link OpenAI cannot fetch | `refused` | no |
| 429 for the rate | `rate_limited` | after `Retry-After`, up to 10 minutes; a longer wait ends the run |
| 503, a connection that was never made; Cloudflare's 521, 522, 523, 525 and 526, a request it could not hand to OpenAI | `unavailable` | after `Retry-After` or 5 s × requests², up to 10 minutes |
| 408, 504, Cloudflare's 524 | `timeout` | no: the run may go on and be paid |
| 500, 502, Cloudflare's 520, an answer that cannot be read | `provider` | no |

A message OpenAI echoes with the start of a wrong key is cut of it before it is stored. `APIError.NeedsVerification` tells the 403 about an unverified organization from other 403s, for the connection's `needs_verification` status.

**Gemini video** (`internal/providers/gemini`, `video.go`). Omni runs as a background interaction:
- `POST /interactions` with `background: true` answers at once with the interaction's id, which the queue saves before the first poll. An answer without a usable id fails the run as `provider` and is not sent again, since Google probably took it. Media go before the words: frames as above, references and a source video inline as base64, never as links, so no presigned URL reaches Google. A download from R2 that the call's deadline or a stop cuts short, and a request cut off before its last byte went out (the request's trace says which), gave Google nothing to start a run from: they are `unavailable` and go again, with nothing paid. A request that went out whole and got no answer may have started a paid run and is a `timeout`. The Files API, which would upload a large file ahead of the request, is not used;
- background needs `store: true`, so Google keeps the interaction: 55 days on a paid project, or what the project sets in AI Studio. framy does not delete it, as it is what `previous_interaction_id` continues. Images still go with `store: false`;
- the poll reads the status: `completed` is the video, `failed`, `cancelled` and `incomplete` end the run with the usage billed and a reason (`NO_VIDEO` and the safety codes are refusals, with the model's words when it gave some), `requires_action` and `requires_continuation` fail it as `provider`, with what the run used by then billed as well, and a status framy does not know is a run still going. A GET that answers 404 or 400 is asked again, as with OpenRouter;
- the video comes inline in base64. When it comes as a Files API file instead, only the file's name is taken from the link, and the download goes to the adapter's own base with the key in the header, which is dropped on a redirect to another host. The run is paid by then, so a download that is throttled, times out or finds Google down is asked for again at the next poll, with Google's wait, until the hour's deadline, which ends the run as `storage` with its cost; only a key that stopped working, money or a filter ends it sooner, with its cost too. A video above 128 MiB ends the run as `storage` with its cost kept, and an answer above 192 MiB as `storage` without one, since it cannot be read;
- the actual cost is the usage tokens by modality: each modality's own rate, the dearest rate of its direction when the catalog has none, thinking at the output text rate and tool use at the input text rate.

**Paid requests.** Before a paid request goes out, the job records `submitted_at`. An attempt that finds it set, with no provider job id and no result, fails as `interrupted` and sends nothing: a worker that died mid-call never pays twice. The person can run it again. What the provider charged for a finished run, and what a grounded run brought, are written down before its results are copied, so an attempt that finds the results kept but the job not ended (the write that ends it failed, or the worker stopped after the copy) ends it as done with them and their cost.

**Results.** A result is copied into framy's storage the moment it is ready. Provider links live from one hour to 48 hours, and OpenRouter's unsigned URLs need the key. An answer with several pictures is billed in full, so a picture of it that cannot be read (not base64, empty) is left out and the others are kept, with the log saying what was lost (`Outcome.Lost`); only an answer with no readable picture fails, as `provider`, with its cost.

**Retries.** Every job has an idempotency key. A retry happens only on a refusal before the generation started, a rate-limit 429 or a provider overloaded or unavailable (503, 529): the job goes back to `queued` until `retry_at`, the provider's `Retry-After` or 5 s × the requests sent squared, at most 10 minutes, and after 5 refused requests it fails, or sooner when the adapter caps the tries of that refusal (an image OpenRouter could not make, 3). A provider that asks for longer than 10 minutes, such as a day's quota spent, ends the run at once with its class, so nobody waits hours for an answer and a free run does not hold its slot and the day's budget meanwhile. A 500 or a 502 is not retried: the request reached the provider, and nobody can tell whether the run was paid. Never after a timeout without asking the provider for the job's status, and never on money or moderation errors.

**Limits.** Two running jobs per person on each stack, counted from `framy.job` under a lock per person, since River has such limits only in Pro. A slot is a run framy is working on, one being sent or made while framy waits on the call; a video out at the provider, which framy only asks about every 30 s for up to an hour, holds none, so a person's pictures do not wait behind two videos. The rest wait in order: a job that ends, or a video that goes out to the provider, wakes the next one, and a job waiting out a refusal lets the others go ahead. Proposal: a queue per chat for Telegram sends.

**Stop.** A queued job is cancelled, and its River job with it. A running image cannot be stopped at the provider: it finishes, goes to the history and is not posted to the chat. Whether OpenRouter can cancel a video job has not been checked. A stop of the process stops taking jobs at once, beside the stop of the servers, and waits for runs in progress up to `JOBS_STOP_GRACE` (3 min 30 s, longer than an image call) and 10 s more for a run cut short to return; the container's `stop_grace_period` is 4 minutes, 20 s more than all that. A run cut short anyway fails as `interrupted`. The queue starts only once nothing else of the start can fail, so a start that fails leaves no run behind it and exits with its error in the log.

## `/img` and `/edit` in a group

### What the commands do

Two commands **(owner, 27 October)**: `/img` makes or edits images, `/edit` edits a video. In a DM the person needs neither: a plain message gets a question, image or video, and the answer starts the same flow (see DM).

| Message | Result |
|:--|:--|
| `/img text`, not a reply | an image from scratch **(owner)** |
| `/img text` in reply to a photo or an image document | that image edited **(owner)** |
| `/img text` in reply to a photo from an album | all photos of the album with one instruction **(owner)** |
| `/img text` as the caption of one's own photo or album | those photos edited |
| `/edit text` in reply to a video, a GIF, a round video or a video document, or as the caption of one's own video | that video edited on the person's video editor, `flux-video-edit` by default **(owner)** |
| words in reply to one's own framy result, where framy is an admin | that result edited, as `/img` (or `/edit` for a video) in reply to it would, the preview to that person alone |
| `/img` with no text | a short answer with an example of the command |
| `@framyin_bot text` at the start of a message or a caption | the same as `/img text`, or `/edit text` with a clip, as the same words are in a chat framy is not in (Guest mode); only the mention gets the hint of a mention. A mention later in a message is talk about framy, and a result posted through inline mode asks for nothing. Telegram delivers such a message when framy is an admin of the group; to a member in privacy mode its documentation promises commands and replies to framy only, so there `/img` is the sure way. Starting a reply to a framy result, the mention makes it this request rather than words to the result. |

**A reply to a result** (`internal/chat/reply.go`). Telegram gives a bot the replies to its own messages even in privacy mode, and a person who answers framy's picture with "make it brighter" waits for framy to go on. Words alone in reply to a result of one's own run start what the command in reply to it would, the words the prompt, but only where framy is an admin, so the preview goes to that person alone. A reply is as often "thanks" as an instruction, so nothing of the run reaches the chat before Create: no chat action, no refusal (the free tier used up, a file too big), and no preview in the chat when Telegram refuses the ephemeral one. Words to someone else's result, to a preview or a card, media of the reply's own, and every reply where framy is not an admin stay unanswered; `/img` in reply works for anyone, anywhere.

`/edit` runs on `flux-video-edit`, the plan of the free edit (see Free tier):
- **Who pays.** The free video first, as for images; the meter is read before the download, so a refusal costs none. Past the week's video, the person's OpenRouter key, if one is connected; without one the answer is when the next free one comes. A message says it as a date and a time in a `date_time` entity (Bot API 9.5, `<tg-time format="dt">`), which Telegram shows in the reader's own time zone, since the bot knows none, rounded up to the minute and in UTC on a client too old for it ("The next free one: 03.11.26, 14:05"). An alert under a button takes no formatting, so it says the wait ("The next one is free in 2 d 2 h") (owner, 31 October, #36). Telegram refuses an alert over 200 characters, so the line fits that in every language with the longest wait. Both say what the allowance is as a whole clause ("you get 1 in any 7 days"), not a bare number.
- **The length.** The free run takes the first 5 s of a longer clip and a run on the key the model's 15 s, and the preview says what was taken. A clip under the model's 0.7 s is refused. When the queue refuses the free run after the meter said it was left, the same clip runs on the key.
- **The other length** is the person's choice **(owner, 27 October)**. Under Create and No the free preview of a longer clip offers it on the key: "All 12 s on your key", or "First 15 s on your key" past the model's 15 s, whose press says where to connect one when no key is connected. The preview on the key offers "First 5 s free" back while the week's video is left. framy keeps only the part a run takes, so the press reads the clip from Telegram again by the `file_id` the run keeps (`chat_run.clip_file_id`), keeps it at the other length, revises the draft with it in place of the old part (`jobs.Queue.Revise` with `Inputs`) and draws the card again. The press is answered at once ("One moment: taking 12 s of the video."), since that takes seconds; when the queue refuses the free length after all, the run stays on the key, as its card shows.
- **The clip** is read from Telegram and kept through the clip pipeline (see Storage), the cut included.
- **The preview card** holds the clip's first frame, or the frame a second in when the first is one colour, and its length as a chip ("0:05"). Its buttons are Create and No, and the other length when there is one. It has no Model or Settings: an edit of a clip keeps its model, and a press from older data changes nothing.
- **The result** goes through the clip pipeline as well, which moves its index to the front and copies the streams when they are fit, and comes as a video (`sendVideo`, `supports_streaming`), always as a reply to the command, and the loop is deleted: a video takes longer than the 25 s a result in place gets, and a reply notifies. One the pipeline cannot read goes as it came, not marked as streaming.
- **The cover** (`cover`, tg#11) is the frame the preview card would show, the first that is not one colour, as a JPEG at quality 90 uploaded beside the video. Clients then open on the same picture instead of one they pick. A frame Telegram would not take as a photo (the sides over 10000 together, or one 20 times the other) goes without a cover, and a cover Telegram refuses with a 400 sends the video again without one: the cover never holds a result back.
- `/edit` on a photo, or on nothing, and `/img` on a video point to the other command.

### Joining a group

- **Add to a group** is a link on the direct chat's panel, beside About (`?startgroup=add`): Telegram lets the person pick the group. The `/start` it may bring there stays unanswered, as any ordinary `/start` in a group does.
- **The greeting.** However framy is added to a group, it says once what anyone's panel there says (`internal/bot/panels.go`, `onMembership`): framy, its hint, and in the quote how to start with `/img`, with Open framy under it, the link to framy's direct chat (see DM). Before, a group heard nothing, and only those who knew `/img` found framy there. It speaks the group's language, or that of whoever added framy while the group has none. It is nobody's panel, so it has no button that acts: the group's language is on an admin's own panel, and Close is only on a panel one person sees. Being made an admin, or anything else that happens to framy in a group it is in, says nothing. A group that becomes a supergroup, as one does when framy is made an admin of it, is a new chat framy may be told it joined; framy remembers for 10 minutes the supergroup a service message names (`migrate_to_chat_id` or `migrate_from_chat_id`) and does not greet it again. A greeting Telegram refuses (framy was removed at once, or may not write there) is logged and fails nothing.

### Albums

Telegram sends each photo of an album as its own message with a shared `media_group_id`, and `reply_to_message` holds only the photo that was answered. There is no method to fetch a message by id, and a bot in privacy mode does not see the other photos at all.

1. **framy as a group admin with no rights.** An admin bot receives every message. framy caches album items in `album_item` for 48 hours, counted from the first time it saw the item, and production deletes the older ones of both bots every hour:
   - `chat_id`, `media_group_id`, `message_id`, `file_id`, `file_unique_id`, size, author and date, and the kind: `photo` (the largest size; a live photo is its still frame, and an image sent as a file is a photo too, since people send files so as not to lose quality), `video`, or `document` for a video sent as a file;
   - never the text or the caption, and nothing from a DM that looks like a key;
   - every message of an album is noted, a command or not, in a group, a supergroup or a DM. An edited message is noted again, since an edit can swap the file, and a replayed update changes nothing.

   When `/img` arrives together with an album or right after it, framy waits for the rest. It keeps in memory when each album last got an item (and forgets an album after a minute), and waits until none has come for 1.5 s, but no longer than 5 s. An album that has been quiet longer is read at once, so a `/img` sent a minute later pays no wait. The wait runs beside polling and never holds it up. framy asks to be made an admin at the first `/img` on an album, not when it is added. Privacy mode stays on: turning it off is global and makes the bot read every message of every group.
   A reply to a picture of a bot's album takes that picture alone and waits for nothing: no bot gets another bot's messages, nor its own, so such an album is never noted. An album of an anonymous admin, or one sent on behalf of a channel, is a person's, though Telegram names a bot as its sender (GroupAnonymousBot, Channel_Bot): framy gets it, and takes it whole.
2. **Without admin rights,** the preview shows the one photo and says "Only 1 photo of the album is taken. Make framy an admin to take whole albums." framy asks Telegram for its own status in the chat (administrator or creator) at every `/img` and caches nothing, since rights change. A DM needs no check: the album arrives whole.
3. **Stage 3:** a `getMessages` method patched into our own `telegram-bot-api`. The server already calls TDLib's `getMessages` for `forwardMessages`, so the patch is about 40–60 lines of C++. Whether Telegram gives a bot messages it did not see is the open part.

An album sent before framy became an admin is not in the cache. The preview always shows what was actually taken, so a wrong guess becomes the person's decision, not a silent error.

### Step by step

What `internal/chat` does today, and what comes later. The bot handles updates one at a time, so a command (at most 4 at once) and a press each run beside polling. Every run is a row of `framy.chat_run` next to its job, so a restart picks it up where it was.

1. **The command arrives.** framy sends `upload_photo`, or `upload_video` for `/edit` (`sendChatAction`), and puts no reaction on the command: the preview comes within a second or two and says the same. A replayed update makes no second draft: the job's key is `tg:<chat>:<message>`. The job exists once the files are kept, so while one command works its key, a copy of it (a replayed update, Image pressed twice in a DM) does nothing, rather than download and keep the files again. An ephemeral command has no message id, and Telegram gives its ephemeral id to another message once it is gone, so its key is `tg:<chat>:e<ephemeral id>:<date>`. framy answers it with a reply only its sender sees, a refusal included, and with a public one when Telegram refuses that.
2. **The sources are collected:**
   - the reply, the album from the cache, or the photos the command is the caption of; for `/edit`, the one clip;
   - downloaded through the local Bot API server (`getFile`, then read from disk);
   - normalized and kept in R2 as the person's uploads (see Storage);
   - at most 10 photos. The rest are left out, and the preview says how many.
3. **A job is created** as a draft with an expiry 10 minutes ahead, which starts again with each change made on the panels. It holds the chat, the topic, the requester, the command, the sources, the prompt, the offer and the settings. The model is the person's default for the kind when they chose one on the site (`default_models`, `internal/chat/own.go`), as the site's composer opens on it: on its free plan when it is a free model whose plan takes the run and a free run of the kind is left, else on a key of theirs that runs it, with the settings and the price the Model list gives it. A default the run cannot go on gives way to framy's choice below: no key runs it, or the key's status is a problem (refused, out of credits, billing, verification), since a free run that works would give way to one that fails; it takes fewer photos than the run has; it left the catalog. Make a video, Make an image and Animate open on the default of their kind the same way. Again, the error card's buttons and an edit of a clip keep the run's model. Otherwise who pays:
   - the free allowance first, on its plan for the number of photos: MAI Image 2.6 Flash up to 5, FLUX.3 Klein up to 10;
   - when the allowance is used up or paused, the person's OpenRouter key, if one is connected and not invalid, on the same model;
   - with no OpenRouter key but one for OpenAI or Gemini, a model that key runs: framy's own pick, as the site's composer opens on one, the first the picker suggests for the run (`recommend` in the overlay) that the key runs, else the first the Model list shows, with the settings and the price the list gives it. The preview shows it on that key and at that price, and nothing runs before Create. Make a video and Make an image past the free tier go the same way. A pick of a free model in Model does not: it asked for that model, so its alert says why it cannot run;
   - otherwise the reason is the answer, with the way on: "Connect your own OpenRouter key on the site", and a button that leads there (`internal/chat/settings.go`). In the DM it is **Connect OpenRouter**, which opens the Mini App's settings at that key (`?settings=openrouter`, `main.js`). In a group and in a guest's chat Telegram takes no Mini App button, and a link to the site would ask the person to sign in again in a browser, so the button is **Open framy**, a link to framy's DM with `/start settings_openrouter`; the panel there has its button at the key, named for it (see DM). A refusal to a press is an alert, which takes no button, and stays text. An edit of a clip keeps its model, so it needs the OpenRouter key.
4. **The preview is sent as a reply to the command** **(owner)**. In a group it goes to the requester alone, as an ephemeral message, when Telegram lets framy send one: framy is an admin, or the command was ephemeral and the preview comes within its 15 seconds. Otherwise, and when the ephemeral send is refused, the chat sees it. An ephemeral send that got no answer may have reached the requester, so the chat does not get the preview too, with their photos and words: the draft is cancelled and the command answered as failed. The replies to an ephemeral command go the same way.
   - **Refusals and hints go the same way** (`internal/chat/chat.go`, `reply`): a command with nothing to make, a missing photo or clip, the free tier used up, a key pasted into the chat. Where framy is an admin they are an ephemeral rich message to the sender, as a reply to the command, or on its own when framy deleted it for a key; what went wrong with someone's command is theirs, and the chat would only read the noise. Elsewhere, and when the ephemeral send is refused, the chat sees them, as the preview.
   - **The message** is a rich message (`sendRichMessage`, Bot API 10.1, `internal/chat/rich.go`, owner, 30 October): the card on top as the message's own picture (`tg://photo?id=card`, uploaded with it), the prompt under it in a quote that folds past 200 characters or 3 lines, what was not taken ("Photos of the album taken: 3"), and the price line where the faces cannot draw the card's label (Chinese, Japanese and Arabic). Then **Model** and **Settings** as sections that open in place (`<details>`), with the current choice in their titles ("Model: Nano Banana Pro", "Settings: 16:9 · 2K", in a DM "Settings: 16:9 · 2K · ×1"). Both are closed when the message comes. Lines break with `<br>`, as a rich message reads its HTML as a page does.
   - **The card** (`anim.Preview`, owner, 27 October): the viewfinder holds the photos, numbered 1…N, or with none a field of dots in the shape of the result and its ratio. Beside it are the maker, the model's name, the settings as chips ("2K", "×2") and the price for the requester: the meter of the free allowance, or the estimate on their key in dollars and their currency ("≈ $0.034", "≈ 1,42 ₴"). The local figure keeps the sign of the dollars, so a ceiling stays one ("≤ $0.19", "≤ 7,82 ₴") and so does a floor; only an exact price in dollars is "≈" in their currency, whose rate is the day's. The price line that stands in for the label in Chinese, Japanese and Arabic says the same in words ("up to $0.19 · 7,82 ₴", "$0.034 · ≈ 1,42 ₴"). The prompt is not on the card. The card is a still, a PNG or with photos a JPEG, so a new model or setting redraws it in milliseconds where a loop would take a second.
   - **Model** lists every model of the run's kind as the site's picker lists it by default (`picker.js`): makers A to Z whatever their case, each under its name even with one model, a maker's families in the catalog's order (featured first, then by name) and a family's variants by `family.rank`, named by the family and the label when the family has more than one. One button a model, the full width, with what it would cost the run: "free" or the estimate on the person's key, in their currency when they chose one. A free model says "free" only while the person has a free run of its kind left (`free.Usage`); past it, it is listed as their key would run it, at its price or as needing a key, since a pick of it then goes on the key. The keyboard's list of an older preview does the same. The current one is marked (`style: primary`). There are no suggestions and no folded rows. A fast mode of a listed model, a variant outdated by a listed one and a vector model (`family.format: vector`: Telegram shows an SVG as a file) are not listed. A model the run cannot take keeps its place as a disabled button with the reason in the site's words: it needs a photo, takes none or fewer than the run has, needs a clip, or needs a key for a provider the person has not connected. A free model runs on its plan when the plan takes the run; past the free tier, and any other model, on the offer of a provider the person has a key for, in this order: the run's provider, OpenRouter, OpenAI, Gemini. A button carries the first 8 hex digits of the SHA-256 of the model's id (`M`).
   - **Settings** is there for a run on the person's key: a free run's settings are fixed, and an edit of a clip has none. It holds the composer's first settings as far as the model has them, a row of values each: the shape 5 to a row, the resolution, the quality and the background under their names, in a DM 1 to 4 results (as many as one run of the model makes, `catalog.AtOnce`; a group and a guest run get one, see below), the length of a video (a long list cut to its ends and 5, 10, 15, 20, 30 and 60 s), its sound as "No sound" and "With sound", and the size where a model has neither a shape nor a resolution, never on a video. The current value is marked. A button carries the setting's name and a hash of the value (`Sresolution#1a2b3c4d`), not its place in the list: the hourly sync may put a new value before it while the preview is up, and the press must still pick the value its button showed. A value the model no longer has changes nothing; the settings are drawn again as they are, with a toast saying so. Buttons sent before this numbered the value (`Sresolution.1`) and are read as they were.
   - **The keyboard:** **Create** (`style: success`), with the estimate when the run is on the person's key ("Create · ≈ $0.14"), and **No** (`style: danger`); under them **Make a video**, **Make an image** or the other length of a clip. A run of a prompt and at most one photo has **Make a video**: the draft is revised in place to the person's default video model where the run can go on it (step 3), else to the weekly free video (HeyGen Video, 5 s at 768p, or Grok Imagine Video Lite while the catalog does not offer HeyGen), the photo its start frame (`frame_images: ["first_frame"]`), on the person's key past the week's video (a video model of their OpenAI or Gemini key when they have no OpenRouter key, as in step 3), and the card is drawn again with the length as a chip. That video has **Make an image**, which goes back to the default image model, or the free image model for its photos. An album has no Make a video, since a video takes one start frame. An edit of a clip has Create and No, and the other length when there is one (see `/edit` above), and no Model or Settings: it keeps its model.
   - **Later:** **Open on the site**, a link to `t.me/framyin_bot/app?startapp=<signed job id>`, because `web_app` buttons work only in DMs.
5. **No:** `deleteMessage` on the preview and the job is cancelled **(owner)**. The panel goes with it.
6. **A pick** of a model or a setting (`internal/chat/panel.go`, `rich.go`) revises the draft in place (`jobs.Queue.Revise`: the offer, the settings, who pays, the estimate):
   - **The settings.** A model on the person's key takes framy's defaults for the shape of the first photo (`catalog.Defaults`, as the API fills a job), what the run set that it takes, and for a video from a photo, the photo as its first frame (`frame_images: ["first_frame"]`) where it has frames. A free model's are its plan's. A setting changes one value.
   - **The message** gets the card drawn again from the run's files in R2. The chat's preview is edited in place (`editMessageText` with the rich message). The requester's own is sent anew with the new card, as a reply to what the first one answered, and the old one is deleted: our Bot API server (telegram-bot-api e3e9dd8, TDLib bc9c263) aborts on `editEphemeralMessageText` with a picture it uploads, and takes every bot on it down with it (four presses on 3 November 2026, four restarts). TDLib fixed that in b7e2d530; editing in place comes back once the server has it. The press lets framy send the new preview, admin or not, so it is answered after the send; when Telegram refuses the press, an admin framy sends it plainly. After a model both sections are closed; after a setting Settings stays open. A press on a disabled model, from forged data or an older message, says why in an alert and changes nothing.
   - **A card that cannot be drawn again** (Telegram or R2 failed) leaves the draft as the card still shows it: the change is taken back, and the press says in an alert that nothing changed. Create runs the draft as it is, so it runs only what the requester saw. An edit in place that got no answer from Telegram (the connection lost, the time up) may have reached it, so once the draft is back its card is drawn once more, and the message shows the draft whichever way the edit went; a refused edit changed nothing. A draft that will not go back is cancelled and its preview deleted, and the press says the preview expired. The other length of a clip goes back the same way, with its file, without the alert: its press was answered already, with the word that the clip is being taken.
   - **In a group** the sections open on the chat's preview for whoever opens them, since they open on the client; only the requester's presses count.
   - **An edit of the command** (`internal/chat/edited.go`) while its preview is up gives the draft the words the message reads now: after `/img` or `/edit`, after the mention, or the whole of a DM's plain message (`jobs.Queue.Reprompt`: the prompt and the estimate, nothing else). The card is drawn again with them and their price first, and the draft takes them after, so Create never runs words the preview does not show: a redraw Telegram refused, or one that never reached it, leaves the draft its words. A change past the 600 characters the card quotes leaves the card as it was, which Telegram answers with "not modified"; the draft takes the words all the same. The photos and the clip the run took stay, and words taken out leave the ones it has. An edit from `/img` to `/edit` or back asks for another run and changes nothing. A preview only the requester sees is sent to them anew with the new words, as for a pick, since an ephemeral rich message with a new card is not edited. After Create an edit changes nothing, and an edit never starts a run, since Telegram sends the edit of a message from days ago too. Before, every edit was ignored, and a typo fixed in the command still went to the model.
   - **A preview sent as a photo** before rich messages keeps working until it expires: Model and Settings on it are buttons as they were. On a preview the chat sees in a group the press sends the requester an ephemeral panel in place of it (`callback_query_id` with `replace_callback_query_message`), and a pick redraws both with `editMessageMedia` and `editEphemeralMessageMedia`. Its settings buttons carry the setting's name and the value's hash as a rich preview's do; those sent before carry the setting's index and the value's (`S0.1`), read as they were. Its list folds the families the person has no key for into one row, "On your own key: 3 more", and a variant on a key not connected says which key in place of its price ("AI Studio key needed"), as the rich message does; no button carries an emoji (`core/docs/panels.md`, R9). A guest run (see Guest mode) keeps these buttons on its text answer.
7. **Create:** the job is queued, the panel is deleted, and `editMessageMedia` turns the preview into the generating loop by its `file_id`, with no upload **(owner)**. A preview only the requester saw is deleted, and the loop comes as a new message the chat sees, a reply to the command unless the command was ephemeral. The loop is drawn when framy starts, uploaded on its first use and sent by `file_id` after that. A `file_id` Telegram refuses is uploaded again; a new message that got no answer is not sent again, nor followed by a line in its place, since it may have reached the chat. An edit by `file_id` (the loop in place of the preview, the error card in place of the loop) goes again by upload whatever failed, since it changes the same message and cannot make two. The caption says "generating · model", and the only button is Stop.
8. **While it runs:** `sendChatAction` every 4.5 s, once for the chat whatever number of runs it has going, and the caption shows the elapsed time every 10 s, less often when several runs share the chat (Limits of the chat). framy reads the open runs every 2 s.
9. **Done:**
   - A result ready within 25 s of Create: `editMessageMedia` turns the loop into it in place **(owner)**.
   - A slower one: a new message as a reply to the command, and the loop is deleted **(owner)**. An edit makes no notification; a reply does.
   - A picture Telegram would not take as a photo (an SVG, over 10 MB, width plus height over 10000, or sides over 20 : 1) goes as a document, named with its extension (`framy.svg`).
   - A video always comes as a reply (see `/edit` above).
   - The caption holds the prompt and the model.
   - The result's `file_id` and `file_unique_id` are kept in `chat_run`, with the message it went out in, which finds the run of a reply to it (`chat_run_result`).
   - **Animate** is the button under an image result: the image becomes the start frame of a new draft of the person's default video model or the weekly free video (step 3), with the image's prompt, on the person's key past the week's video, as a command's draft goes (step 3). Its preview is a reply to the result, and in a group it goes to the requester alone: the press lets framy send an ephemeral message within 15 s, admin or not (`callback_query_id`). A double tap within 5 s is one press, and the press's id is the draft's key, so a replayed update makes no second one. A video result has no Animate, nor has an SVG: no video model takes one as a frame.
   - **Again** is under every result of a run made in the chat (`internal/chat/again.go`): a new draft of the run with its prompt, its files, its model and its settings, whose preview replies to the result as Animate's does, the press's id its key. Who pays is asked again: a free run goes free while the tier has a slot and on the person's key past it (on a model of their OpenAI or Gemini key when they have no OpenRouter key, as in step 3), so the preview shows the price before anything runs, and a run on the key needs the key still there (the press's answer says "OpenAI key needed"). A file of the run deleted on the site since leaves nothing to run again, and the answer says so.
   - **Original** is under an image that went as a photo: the file as the model made it, as a document replying to the result, since a photo is Telegram's copy (at most 2560 px on its long side, a JPEG, no transparency). It goes once, and the button goes from under the result; a press from a keyboard Telegram had not changed yet sends nothing within the hour, unless framy restarted since. A picture that went as a document has none.
   - A result of the site in the DM has Animate and Original, not Again: a run of the site may hold what the chat's preview cannot show, and the site has its own Again.
   - **Later:** **Open on the site**.
10. **Failure:** `editMessageMedia` into the error card (media cannot turn back into text). The card gives the reason in plain words: the model refused, the model does not take real people (`faces`: try another model), the model refused its own sound (`sound`: turn sound off and try again), the provider does not serve the country of framy's server (`region`: try another model), the person's key is out of credits (naming its provider: "Your OpenRouter key is out of credits."), the provider refused the key, the model took too long, the result came out but framy could not keep it (`storage`, the site's words), the model could not make it, or something went wrong on framy's side (its own failure, a model it has no way to run, or its key on a free run), in the words the site uses for that. Under it is what helps, as on the site's card of a failed run (`errors.js`), only the requester's press acting:
   - **Try again**: a new draft of the run, as Again makes one, its preview replying to the card;
   - **Another model**: the same draft with the list of models open;
   - **Try without sound**: after `sound`, on a run that had sound on, the same draft with `generate_audio` off.

   `faces`, `moderation`, `refused`, `region`, `invalid_request` and `no_adapter` get Another model, and `sound` gets Try without sound, or Try again when the run had no sound to turn off. The person's key out of credits gets **Top up OpenRouter** (or OpenAI, AI Studio), a link to that provider's billing page as on the site's card (`errors.js`, `BILLING`), and Try again for after it, which shows the price before anything runs. A key the provider refused gets **Replace the … key**, the way to the settings at it as under a refusal (step 3): the Mini App in the DM, framy's DM elsewhere. On a free run either is framy's key, and Try again goes on the person's key. The rest get Try again and Another model. An edit of a clip keeps its model and has no Another model. A card that cannot be shown is a reply with the same line and buttons, which takes its place.
11. **Stop:** a queued job is cancelled and the loop deleted. A running one cannot be stopped at the provider: it finishes in the person's library on the site and is not posted. The answer to the press is then an alert that says the model had already started and what the run costs: the person's key pays for it, named by its provider, or it counts toward the free images or the free videos. Without it the loop leaving the chat reads as the money or the free run given back. A job that ended as Stop came cannot be called off either: its loop stays, and its result, paid for already, or its error card takes the loop's place at the next round, as at any end.
12. **An unconfirmed preview** expires with its draft after 10 minutes without a press or a change, and is deleted. A press on it after that says how to start again in the words of the way the run began: `/img` or `/edit` again in a group, the message again in a direct chat, framy mentioned again in guest mode. A press by someone else says only the one who asked can press, since a direct chat's run and a guest run had no command.

In groups and in guest mode one run makes one result, and the card offers no count: a group would get four pictures for one command, and a guest run's answer is one message. A count pressed there anyway changes nothing. In a DM a run on the person's key may make up to four, as many as one run of the model makes (`catalog.AtOnce`), and the price says so. They come as one album: a new message with the caption on the first, since an album cannot take the loop's place, and the loop is deleted. An album takes no keyboard, so there is no Animate, Again or Original under it, as under a press of frames from the site; the run keeps the first picture as its message, and a reply to any of the pictures changes that picture (DM below).

### Who can press

- Only the requester can press the buttons of a run, Animate on its result included. Anyone else gets a short alert from `answerCallbackQuery`.
- Proposal: group admins can also press No, to clean up.
- State changes are compare-and-set, so a double tap cannot start two runs.
- What the flow keeps in memory of a run goes once it no longer matters (`internal/chat/chat.go`): a run's mutex while a press or the delivery holds or waits for it, a double tap of Animate, Again or the card's buttons for its 5 s, Original's once for an hour, and the rest when the run ends. A result of the site given back after a failure is remembered until it goes, ends, or is an hour past its last try. A press on a result from a week ago leaves nothing behind.

### Limits of the chat

- **Message rate:** Telegram allows about 20 bot messages a minute in a group, and past that answers with 429 and how long to wait (`retry_after`). tg waits that out once and sends again; a second 429 comes back to framy (`internal/chat/telegram.go`):
  - **A 429 holds the chat** until its wait is over. A call that answers a person, a command or a press, waits for the hold and then goes, unless the hold is longer than 30 s, when it is refused at once rather than keep one of the four command slots. The rounds that follow the runs and send the site's results do not wait: a held chat gets no call in the round, and its runs move on in a round after the hold, so one busy group never stalls the others. A delete that cleans up after framy's own message (the loop under a result, a preview that expired, a question that was answered) does not wait in the call either: to a held chat, or answered with a 429, it goes in the background once the wait is over, up to three holds, since left out the message would stay in the chat for good.
  - **Progress shares the chat's pace.** The chat action goes once per chat or topic every 4.5 s, whatever number of runs are going there. A chat takes at most one caption every 6 s, and a run's caption is due every 10 s or every 6 s times the runs going in the chat, whichever is longer: three runs at once tell their time every 18 s each, about 10 edits a minute, and leave the rest to previews and results. A call that only shows progress is cut short after 5 s, so tg's own wait inside it does not hold up the round, and the wait it was told still holds the chat.
  - **The site's results** are given back on a 429, which delivered nothing, and go once the wait is over. A send that never reached Telegram delivered nothing either: the file was not read from the bucket, the video not readied, or no connection to the Bot API server was made, as while it restarts. Those are given back and tried again 2 s later, then twice as long each time up to 5 minutes, while the result's hour lasts (`internal/chat/site.go`, `releaseSite`); before, they were marked failed and the person never got them. Any other failure Telegram refused, which a second try would not change, or may have delivered, a 5xx included, since a gateway answers one while the send goes on behind it: those are not sent again (at most once).
  - **A result Telegram refuses** with a 403 (the bot was removed or blocked, or may not post there) or a 400 (the chat, the topic or the right to send that media is gone) would be refused the same way every time, so the run ends at once as `gone` (`internal/chat/deliver.go`): the loop, where it can still be changed, says the result is in the person's library on the site and loses its Stop, and an error card neither shown nor replied leaves the run `failed`. Any other failure of a result or a card is tried again 2 s later, then twice as long each time up to 5 minutes, and given up an hour after the job ended; the first try after an outage is made however old the run is.
  - **A result goes once, as far as framy knows.** One that went out is recorded even when a stop or a database hiccup cuts the record short: the next round records it and sends nothing again. A stop starts no new round and gives the deliveries in flight, in the chat and of the site's results, 15 s to finish, as the bot gives the updates it took. What is left is a crash between a send and its record, after which the restarted framy sends the result again: in the chat a result is sent at least once, where the site's results in the DM are sent at most once (see DM), because a person waiting in the chat under a loop that never ends is worse off than one who gets the picture twice.
  - **A command a stop leaves waiting.** Four commands are worked at once; the bot takes updates from Telegram and confirms them as soon as each is handed on, so Telegram gives a command waiting for a slot to no one again. At a stop the commands that have a slot go on for the bot's 15 s; one still waiting, or one of the batch already taken that finds no slot free after the stop, is not started half-way, and its sender is told framy is restarting and to send it again in a minute, in the chat (to them alone where framy is an admin) or in the answer to a guest message (`internal/chat/chat.go`, `withSlot`).
  - Not done: a queue that spaces every send of a chat ahead of a 429. The pace above keeps framy's own traffic under the limit; a 429 that still comes is waited for, not guessed.
- **Anonymous admins and channels:** a message an anonymous admin sends comes from `GroupAnonymousBot` with the group as `sender_chat`, and one a person posts as a channel from `Channel_Bot` with the channel; neither names the person. A run is a person's, who pays for it and alone presses its buttons, so `/img`, `/edit` and the mention from them make none, and the chat is told why in a reply: send it from your own account, or turn off anonymity in your admin rights (`internal/bot/panels.go`, `sentAsChat`). The reply cannot be ephemeral, as there is no one to send it to. A key pasted after such a command is deleted as anyone's is, and the answer is the one about keys. A channel's post forwarded into its discussion group (`is_automatic_forward`) is no request and gets nothing.
- **Video in large groups:** sending one can return `message_id = 0` while the server re-encodes. Such a message is not edited or deleted right away. The run keeps the file it went out as, and the first press of Again on the message that appears is taken as on the result when that message carries the file, or is framy's video answering the command once the file changed in the re-encoding; its id is recorded then (`internal/chat/press.go`), so the new draft answers it and later presses on any other message do nothing.
- **Media to text:** media cannot become text again. Back to text means delete and send anew.
- **Answers to presses:** an alert or a toast is at most 200 characters, and Telegram refuses a longer one outright, so the button only stops spinning. A test holds every answer to that in every language with the longest values it takes (the German free-limit alert was 209 with a wait of 23 hours and was shortened); one longer still, from a new translation say, is cut with an ellipsis rather than lost.
- **Button labels:** Telegram gives the buttons of a row equal widths and cuts a label that does not fit, and half a row of a phone 320 to 375 points wide shows about 14 characters. Two buttons share a row only when both labels are that short; a longer one takes a row of its own, as Belarusian "Паспрабаваць яшчэ раз" does on the error card, and English "Top up OpenRouter". A label alone on its row stays within about 33 characters in every language. Create and No stay one row: the price on Create may be cut on a narrow phone, and the card shows it whole.

### Loops and cards

`internal/anim` draws the pictures on the CPU, without a browser, and hands the bot a file with its size and length. Every picture is 1280×720, 16:9: a chat shows it as wide as a video and lower than a square, which looked cramped. The preview, the loop and the card are the same size, so the message does not jump when one turns into the next.

- **Look.** The field colour of the Avatar proposal and white. The name in lowercase and the numbers are Sofia Sans Extra Condensed; the card's line is Sofia Sans, shaped with the person's language, because the font draws Bulgarian Cyrillic unless told it is Russian. It has local forms for Russian only, so Ukrainian and Belarusian are shaped as Russian: told Ukrainian, it kept the Bulgarian в and т. Square corners, stripes 14 and gaps 8 (7 : 4). The viewfinder of four brackets is the frame of all three.
- **Preview card.** The viewfinder on the left, 568 px wide; the column on the right holds the maker in Sofia Sans caps, the model's name in the display face at up to 132 px in at most two lines, the chips as white squares with the figure in the field's colour, like the photo numbers, and the price at the bottom. Its words are drawn only where the faces have the letters; the chips, the ratio, the prices and the meter need none. ₴ and ₽ are not in the faces, so the local price is written with the code there ("≈ 1,42 UAH").
- **Album loop.** Since the preview card the chat does not send it; `Renderer.Album` still draws it. One to ten photos, JPEG or PNG as `internal/media` writes them, 4 s. Each photo keeps its shape in rows, with a white square and its number at its corner. The rows are the split with the biggest product of the smallest photo and the whole collage: no photo is a sliver, and five photos of mixed shapes go in two rows instead of a thin strip across the wide frame. The album floats as one piece: it rises 12 px over a soft shadow and sinks back, and no photo ever leaves its place, so the picture always reads as one album in order. It moves by whole pixels, so the photos stay as sharp as at rest and the file stays small. The loop starts at rest: that is the frame Telegram shows as its still.
- **Generating loop.** 7.2 s, no text and no language. A halftone of dots fills the viewfinder and keeps turning from one figure into the next: a blob of three balls, a wave, a heart, two mountains with a sun, a flower, a crescent, and round again. Each figure has 1.2 s; the next runs into it across the grid in 0.5 s, left to right and back by turns, with a little of every dot's own in it. While it holds, a figure moves (the balls roll, the wave runs, the heart beats, the sun bobs, the flower turns, the crescent rocks) and drifts 24 px sideways, so something moves in every frame while only the dots at its edge change. None of the figures is a logo: the first version gathered the dots into a four-pointed spark, which read as Gemini's. The loop is drawn once, kept under a key that changes with the design, and sent by `file_id`.
- **Error card.** A PNG with the cross in the viewfinder on the left and the bot's line beside it, in at most four lines. The faces cover Latin and Cyrillic, which is thirteen of the sixteen languages. For Chinese, Japanese and Arabic the card has no line (`Media.TextDrawn` is false) and the bot puts the line in the caption.
- **Encoding.** libx264 on four threads, CRF 22, yuv420p, BT.709, `+faststart`, 30 fps, no sound track: what Telegram plays as an animation. ffmpeg runs with an empty environment and reads only the pipe the frames come through. Every loop is a whole number of turns, so its last frame leads into its first, and a test holds it to that. yuv420p keeps one colour for every 2×2 pixels, which costs about 2 levels on average at the edges of photos and dots whatever the quality; the test of the video checks the colours on the plain field, where a wrong matrix or range shows.
- **Measured** on 10 cores of an M1 Pro, ffmpeg included: the album of ten 2048 px photos in 0.7 s and 142 KB, the generating loop in 0.6 s and 533 KB, a card in 45 ms and 27 KB. With Go limited to one core (ffmpeg still uses all) the album takes 1.8 s and the loop 1.3 s. x264 on four threads instead of its own 44 encodes a loop's frames about 0.2 s slower. The ffmpeg in the image (Alpine 3.24, FFmpeg 8.1.3, on ws04) gives the same sizes within 10 KB, and the tests pass there.

## DM

- **No command needed (owner, 27 October).** A plain message, with or without photos or a video, gets a question: an image or a video. The answer starts the same flow as `/img` or `/edit` in a group, with the message as the prompt and its media as the sources. Built (`internal/chat/ask.go`):
  - **The question** is a reply to the message with two buttons, Image and Video (`d:<message>:i` and `d:<message>:v`). The answer deletes it and starts `/img`, or the weekly free video with the photo as its start frame, as Make a video does in a group. A replayed update of a message already answered asks nothing.
  - **What can go only one way goes there at once:** words with a clip go to `/edit`, and an album with words to `/img`, since a video takes one start frame.
  - **framy's mention is not a word of the prompt.** Telegram offers inline mode as one types `@framyin_bot`, and a person who sends that as text anyway, or writes to framy as in guest mode, means the words around it: the mention is left out wherever it is, in any case. Other mentions stay, as the person's words. A photo whose caption is the mention alone is media without words.
  - **Media without words** gets a line on what to send: the same again with a caption, or a reply to it with a few words. A sticker, a voice message or a service message gets nothing.
  - **An album** is answered once, after the same wait as in a group, about its item with words, or its first; an item that comes later starts nothing.
  - **A reply to framy's own message** takes its picture only when it is a result: a reply to a preview, a question or a panel is about its words alone. Every picture of framy's album is a result, since framy sends albums only of results (several of a run, a press of frames from the site), and their run notes the first picture alone: a reply to the third picture is about the third picture, and gets the question as a reply to one result does.
  - **An edit** of the message while its question waits is what the answer takes; while its preview is up, it changes the run's words as in a group (step 6 there); after Create, nothing.
  - **After a restart** framy has forgotten what each question was about (it keeps that in memory for 10 minutes), so the answer reads the message from the question's reply, which carries the message but not what it answered. A question whose message is gone, or an answer from someone else, says to send the message again.
  - Commands, keys and anything starting with `/` never reach it.
- **The same flow.** An album arrives whole here, but its items are still noted and waited for as in a group, with the same 1.5 s wait, because Telegram delivers them as separate messages.
- **Confirmation.** Proposal: in a DM the person can turn confirmation off.
- **`/start`:**
  - a panel with the free allowance left, the connected providers, the default models, the language and the currency;
  - "Open framy" as a `web_app` button.
  - The menu button opens the Mini App.
  - `/start settings_<provider>` comes from the button under a refusal or an error card outside the DM: the panel is the same, and its button opens the settings at that key and says so, "Connect OpenRouter" or "Replace the OpenAI key" when one is connected. A provider framy does not know leaves the panel as it is. Messages already sent carry the parameter, so it is read for good.
- **What the panel shows today** (`internal/bot`, a direct chat only; a group's panel shows nothing about the person):
  - the free images and videos left, as `free.Usage` counts them: "4 of 5 left in any 24 hours", "1 of 1 left in any 7 days". The site says the allowance in the same words, in its settings, on the picker and under the price before sign-in ("5 free in any 24 hours", with "Sign in to create" on the button beside it), never "a day", which reads as a calendar day that starts again at midnight. The windows are words in the strings, so a test fails when `free.ImageWindow` or `free.VideoWindow` changes;
  - the connected providers by name (OpenRouter, OpenAI, AI Studio) in the order of the About card, with a status word only where the status is `invalid`, `needs_billing`, `needs_verification` or `no_credits`, and "none yet" while nothing is connected, which includes a framy without a KEK file. Not a character of a key is shown, not even the last four;
  - the language by its name, without the flag, and the currency: the person's choice, else the language's (`uk`, `be`, `pl`), else USD. The bot has no country;
  - the default models are left out: the site's settings keep them (migration 025), and the panel does not show them yet;
  - last, how to start, as a group's panel ends with `/img`: a description for a new image or a video, or a photo or a video with a caption to change it, and nothing runs until Create. Until alpha.4 this line said framy was not open yet, long after it was.
- The reads are made when the panel is drawn, on `/start` and on Back, under one 3-second deadline. A read that fails is logged and its line is left out, so the panel always answers.
- "Open framy" is the one Primary button of the panel, above the tabs. Telegram takes `web_app` buttons only in a private chat, so a group's panel has a link in its place, its Primary too, above the group's language and the tabs: Open framy opens framy's direct chat with `/start group`, whose panel opens the Mini App signed in, with the person's history and settings. A link to the site would ask the person to sign in again in a browser, as under a refusal in a group (step 3). Until then a group's panel had no way to either. Both buttons and the menu button need an https `SITE_URL`, and the link also the bot's name; without them the button is left out and the menu button is left as it was. At start the bot sets the default menu button (`setChatMenuButton` without a chat), a `web_app` button labelled "framy" in every language.
- **Add to a group** is the last row, beside About, with no colour: it adds framy to a group the person picks, which framy then greets (see Joining a group).
- **Help**, a tab of the panel in a DM and in a group, says every way in: a plain message in the DM, `/img` and `/edit` in a group, the bot's username with words in a chat framy is not in (Guest mode) and typed alone for past results (Inline mode), what the preview shows before Create, the free allowance, and the site's address, linked, when `SITE_URL` is https: the other lines send the person there for keys, and a group's Open framy leads to the direct chat, not to the site. It names the bot by the username it runs as, so the test bot says its own. A group's panel names `/img` and `/edit`.
- **Results made on the site** come here when the person has allowed it (`telegram:bot_access` at sign-in, or `/start`). Built (`internal/chat/site.go`):
  - **What is sent.** A job of the site (`surface = 'site'`; the Mini App's are in Telegram already) that ended done in the last hour and is not deleted. framy reads them every 5 s, 20 at a time, four sent at once. One that ended earlier stays on the site: held back by an outage, it is old news by then.
  - **A press of several frames** (`batch`, Frames above) waits until every job of it has ended (done, failed, cancelled or expired), and then comes whole, as one album (owner, 31 October). Its hour counts from its last end, so a slow video does not leave the pictures made with it behind, and every frame of it comes however long before that its own job ended: a person's jobs run two at a time and wait for a stopped stack, so a press can last longer than the run deadline (migration 031 finds a press by its last end). The query puts a press's jobs next to each other, and a round of 20 that may have cut its last press leaves that press to the next round. The album is in the order of the frames, whichever job made them. Its caption says once what the frames share and the rest a line per frame, numbered as Telegram numbers the items: the prompt as a quote and `1 Model A`, `2 Model B` under it; the model once at the end when only the prompts differ, each prompt cut to 120 characters on its line. The caption always fits Telegram's 1024 characters, counted as Telegram counts them, since a longer one loses the whole album: past that the prompts give way, every frame's alike, and the numbers and the models stay whole (a press of six frames, each with a prompt of its own and a long model name, went over; `internal/chat/site.go`, `albumCaption`). Pictures go as photos, or all as documents when one is no photo; videos go readied as one alone, each with its cover (`InputMediaVideo.Cover`, tg b5a8288), and again without covers when Telegram refuses them. Each job gets its chat run on its first frame's message, so a reply to that frame works as on any result; there is no Animate, since an album takes no keyboard. A press that is one result after the others failed comes as any result, with Animate. It ends whole too: off, closed or failed for all its jobs, and a hiccup gives the whole press back.
  - **At most once.** A row of `site_delivery` (migration 020) is written before anything goes out: `sending`, then `sent` with the message, `closed` or `failed`. A send a restart cut short stays `sending` and is not tried again, since it may have arrived. A send Telegram answered with 429 delivered nothing: the claim is given back, and the result goes once the wait is over. So did a send that never reached Telegram, whose claim is given back and tried again later (Limits of the chat).
  - **May the bot write?** A chat action (`upload_photo` or `upload_video`) goes first and tells before any upload. A 403 (never started, blocked) or a 400 (a chat the bot does not know) closes the result: the person gets nothing and is not asked again for it. Any other failure gives the claim back, and it is tried again 2 s later, then twice as long each time up to 5 minutes, while the result's hour lasts; a 429 goes once its wait is over.
  - **How it looks.** The same caption as in a group, the prompt and the model. One image comes with Animate, as a photo or as a document when Telegram would not take it as a photo (an SVG as a document, without Animate); several pictures come as one album, the caption on the first, all as documents when one is no photo, and without Animate, since an album takes no keyboard; a video comes with its cover, and a run Continue joined to its clip comes as the joined clip, as the site shows it (owner, 31 October). It is a new message that notifies.
  - **After it.** The job gets a chat run that is done in the DM, so Animate and a reply to the result work as on any result there. The run keeps which file its message is when that is not the first result (`chat_run.result_asset_id`, migration 028, indexed by migration 033 so that deleting a file does not scan every run): Send to Telegram reuses the message's file only for that one, so the run's own video is not sent as the joined clip.
  - **Turned off.** `deliver_to_telegram: false` in the settings (`profile.deliver_to_telegram`, migration 025) stops it: a result that ends while it is off is written to `site_delivery` as `off` and is not sent later, when the person turns it on again. Blocking the bot or deleting the messages still works as well.
- **Message effects.** A finished result can carry a message effect (DMs only).
- **Progress is the loop**, as in a group: one message whose caption has the time and whose Stop is a button under it. The result and the error card take the loop's place.
  - **Not a draft.** framy streamed the progress as a draft (`sendMessageDraft`, Bot API 10.3) with Telegram's own Stop from 30 October, and took it out the same day: the draft is a second message under the loop, which said the same thing twice, and a plain draft is text only. A rich draft (`sendRichMessageDraft`) can show media by `file_id`; one holding the loop itself with the time and `can_stop` would be a single message again, and is not tried yet.

## Inline mode

`@framyin_bot` typed in any chat lists the person's past results, to send again. Built (`internal/chat/inline.go`):

- **What is listed.** The person's results that went out in Telegram as a photo or a video, newest first, 20 at a time; scrolling asks for the next 20, by the last job id. What is typed filters by the prompt, in any case, and `%` and `_` are only themselves. A deleted job is left out. Telegram takes a `file_id` again only as what it was sent as, and framy answers with cached photos and videos, so a result sent as a document, and an album's other pictures, are not listed. What a result went out as is `chat_run.result_file_type` (migration 021); a run that ended before it has none and is not listed.
- **How it is sent.** By its `file_id`, so nothing is uploaded, with the caption it had: the prompt and the model. The title is the start of the prompt on one line, the description the model. No buttons: a press on an inline message carries no message and comes from a chat framy may not be in, so the bot only answers it.
- **The button** above the results is "Open framy": the bot's chat with `/start inline`, whose panel opens the Mini App signed in. It is not a `web_app` button: Telegram gives a Mini App opened from inline mode no `initData` (`WebAppInitData` is empty for inline mode and for keyboard buttons), so the site could not sign the person in and asked them to sign in with Telegram inside Telegram. With nothing found it says "No results. Open framy".
- **Cache.** The answer is personal and Telegram keeps it 5 s, so a result just made shows up on the next query.
- **Typing.** Telegram sends a query for every letter and shows only the answer to the last, so a person's new query ends the one before it, and a first page waits 150 ms for the next letter before it reads the history: "a fox" typed at speed is one read of the history, not five, and its answer comes 150 ms later. At most 8 answers are read at once, whoever types. The bot records the person in core on their first query and then at most once a minute, not once a letter; any other update records them as always.
- **BotFather.** Inline mode is on (`/setinline`) for @framyin_bot and @framytest_bot since 30 October 2026, with the placeholder "Search your images and videos".
- **Not yet:** `chosen_inline_result` and editing a sent inline message.

## Guest mode

`@framyin_bot …` in a chat framy is not a member of (Bot API 10.0). Telegram sends the bot that message as `guest_message`, with the message it replied to, and the bot answers it once with `answerGuestQuery`. The answer is an inline message, which only its `inline_message_id` reaches. Built (`internal/chat/guest.go`, `internal/bot/guest.go`) and tried live on framy-test (T9, below):

- **The run is a group's run with one message.** The preview, the loop and the result or the error card are edits of the answer by `inline_message_id`, in that order. The requester presses as in a group, and anyone else gets the same alert. A run is a guest one when its `chat_run` has an `inline_message_id` (migration 022), and its job's surface is `guest`.
- **What is read.** The text of the message without framy's mention, in any case; other bots' mentions stay, since up to three guest bots can be summoned at once. The sources are those of `/img`: the photo replied to, or the message's own. framy is not in the chat, so of an album only the photo replied to is taken. A video gets a line that framy changes videos in a direct chat. No text gets a line on what to write.
- **The language** is the person's, not the chat's: framy does not know the chat, and its id may name another chat framy is in. For the same reason only the person is recorded in `core`, with no chat.
- **No uploads.** Telegram takes no upload in an inline message, so every picture goes by a `file_id` Telegram has of it or by a signed link Telegram fetches from framy (`SharePath`, as in Send to Telegram):
  - the preview card, drawn from the run's files in R2 when Telegram fetches it, as a JPEG of 1280 px;
  - the generating loop by the `file_id` a chat run got for it, else by a link to the MP4;
  - the result by a link: a picture as a JPEG framy makes, an MP4 up to 20 MB as it is kept;
  - the error card by its `file_id`, else by a link.

  Each link carries a counter (`?v=`), so Telegram never shows a card it fetched before a pick. Without an https `SITE_URL` there is nothing to fetch from: a guest message gets one line that framy cannot answer there, with the link to framy's direct chat, which needs no site.
- **The answer is text** with the caption and the buttons a group's preview has, and the card above it as the link's preview (`link_preview_options` with `url`, `prefer_large_media` and `show_above_text`; the link is not in the text). Text, because an inline message's text can become a picture (`editMessageMedia`) or one line, while a picture never becomes text again. The run is recorded before the answer, since Telegram may fetch the card while it answers, and the answer's `inline_message_id` after it, which the presses find the run by: a database hiccup there is tried twice more, and one that lasts turns the answer into the failure line with no buttons and closes the run, rather than leave buttons that do nothing. A refusal (no free run left, a refused model) is a text answer with no card, with the link to framy's DM at the key when a key would lift it, and so is a failure before the draft. An error card on the person's key has the way to fix it, as in a group, and no Try again: framy is not in the chat to post a new preview.
- **Model and Settings** change the answer's buttons (`editMessageReplyMarkup` by `inline_message_id`), and a pick edits the text with a new link (`editMessageText` with `link_preview_options`), so Telegram fetches the card drawn again.
- **Create** turns the answer into the loop with Stop. When Telegram takes no loop, the answer becomes the card as a photo with the same caption and Stop.
- **While it runs** the caption shows the elapsed time every 10 s. There is no chat action: framy is not in the chat.
- **Done.** The answer becomes the result, with the prompt and the model and no buttons. One result per run, as in a group. A picture or a video Telegram cannot be given (a WebM, an MP4 over 20 MB), or one it refused, stays in the person's library on the site, and the caption says so.
- **Nothing can be deleted** in an inline message. No and an expired preview shrink the answer to one line, "Cancelled.", with no card and no buttons. Stop on the loop cannot go back to text: the answer becomes the card the run started from, with the prompt and "Stopped.", and no buttons.
- **A reply to an open answer.** A guest message that replies to framy's answer while it still has buttons gets a line to use them, not a second run off the same words. framy's answer is told by its sender or `via_bot` and its `reply_markup`, which tg does not model, so both are read from the raw message. A reply to a result changes the result, as a reply to one does in a group.
- **BotFather.** Guest Mode is turned on in BotFather's Mini App, and is on for both bots (`bot_guestchat` in their profiles, 31 October).
- **T9, 31 October on framy-test.** In a new group without the bot, `@framytest_bot …` in reply to a photo got the answer with the card drawn from that photo, so `getFile` takes a `file_id` from a guest message's reply, and Telegram's fetcher got the card through Cloudflare while answering: a 1280×720 photo preview marked large. Presses come as callback queries. One answer took 8 edits, 3 of them new texts with a new card link, each fetched again. A reply to the open answer got "This one is still open: use its buttons", so the reply carries the answer's `reply_markup`. No turned it into "Cancelled." with no card and no buttons. Generate, the loop and the result were not pressed in this check; guest runs from private chats on 30 and 31 October went through them: eight done, seven of them free on MAI and one on the person's key, and one failed. Whether the preview stands above the text was not seen through the client API.

## Mini App

The same frontend as the site, on the site's origin ([#21](https://github.com/FreshLabDev/framy/issues/21)). It opens from:
- the menu button beside the input field of every direct chat, set at start (`setChatMenuButton`, `internal/bot/commands.go`);
- **Open framy** on the DM's `/start` panel, which is also where the button above inline results leads (Inline mode);
- the Main Mini App in the bot's profile, where it is turned on in BotFather (Telegram setup).

Built (`internal/web/app/src`, Telegram's part in `main.js`):

- **Telegram's controls.** MainButton is the composer's main action: Create, or the step that comes before it (sign in, cut the clip, add a key). BackButton closes a sheet or the full view, and takes the library back to the composer. SettingsButton in the Mini App's menu opens the settings once the person is signed in. The header, the background and the bottom bar take framy's colour, a vertical swipe does not close the app, and the layout keeps to the safe areas through CSS `env(safe-area-inset-*)`.
- **Viewing a result** opens framy's own full view, and a video's player goes fullscreen through the browser's Fullscreen API (on an iPhone, its own player).
- **Sending a result** (#37). `POST /api/files/{id}/share` saves the result as a prepared inline message for the person (`savePreparedInlineMessage`, any kind of chat), and the Mini App passes the `id` it answers to `Telegram.WebApp.shareMessage`, where the person picks the chat; framy need not be in it. Built (`internal/chat/share.go`):
  - A result that went out in a chat goes by its `file_id`, as what it went as, with the caption it had, as in inline mode. A chat run keeps the first message of an album, so that is the job's first result only.
  - Any other goes by a link Telegram fetches from framy, `SITE_URL/share/<token>`: a photo has to be a JPEG of at most 5 MB, so framy makes one when the link is fetched, 2560 px on the long side at most and see-through parts on white, with a thumbnail of 320; a video goes as it is kept when it is an MP4 of at most 20 MB, with a cover of its first frame that is not one colour. A WebM, a video over 20 MB, another kind of file (an SVG among them), or no https `SITE_URL` is refused with 422 `not_shareable`, and the Mini App offers Download instead. Under a WebM or an SVG it shows no Send to Telegram at all.
  - The token is the person, the file, the part and an expiry an hour off, signed with HMAC-SHA256 by a key made when the process starts, so no secret is added and a restart ends every link. A link of a result deleted since, of another part, forged or ended is a 404. Two pictures are made at once; a fetch waits up to 20 s for its turn.
  - Not checked yet against Telegram: whether it fetches the links when the message is saved or when it is sent, and that its limit on a video by link is 20 MB. A prepared message lives 24 hours, the links one, so a share that waits longer than an hour may fail.
- **The original:** `downloadFile` with the result's presigned R2 link, which asks for an attachment and which the bucket's CORS lets Telegram Web fetch (Security and operations). Before Bot API 8.0, or without a link, the button is an ordinary link.
- **Settings** are on the server (`PATCH /api/me`). Of them the browser keeps only the language (`localStorage`), so the first paint is in it before `/api/me` answers. `sessionStorage` holds, for the tab, the prompt being written and the Mini App's `initData`.

- **Later** (#21):

## Storage and retention

- **Inputs** from Telegram and the site go through one ffmpeg subprocess: HEIC, AVIF, WebP, JPEG and PNG, iPhone's tiled HEIC included. ffmpeg decodes HEIC 5–6 times faster than pure Go (0.13 s against 0.75 s for 12 MP). The steps:
  1. **Upload:** streamed to disk under `http.MaxBytesReader`.
  2. **Format:** sniffed from the first bytes, never from the MIME type: Safari sometimes converts HEIC and sometimes does not.
  3. **Check:** anything above 64 MP is refused. The size is read by framy from the header (JPEG SOF, PNG IHDR, the WebP canvas, the largest `ispe` of a HEIF) before anything decodes the file, and `ffprobe` and `ffmpeg` run with `-max_pixels` as well, so a header that lies does not get further.
  4. **Convert:** the file goes under a name framy picks, ffmpeg reads it with the demuxer of the sniffed format (never its own guess) and `-protocol_whitelist file`, with an empty environment and a timeout. It rotates by the orientation and drops all metadata with GPS (`-map_metadata -1`), and the long side becomes at most 2048 px. The output is JPEG, or PNG when there is alpha.

  HEIC cannot come through a pipe, so a temporary file is needed. A Telegram photo is up to 10 MB, width plus height at most 10,000, a ratio of at most 20. Inputs are kept with the job.

  What ffmpeg does on its own and what framy adds (`internal/media`, checked on FFmpeg 8.1 in the image and 9.0):
  - **Tiles.** An iPhone HEIC is a grid of 512 px tiles. `-vf` cannot read it; the filter graph starts from the grid, `[0:g:<n>]`, and the tiles come joined and cropped.
  - **Threads.** ffmpeg gives every decoder and encoder a thread per core, and every tile is a decoder of its own: a 12 MP HEIC (48 tiles) started 438 threads on ten cores, and a 24 MP one 544, past the container's PIDs, for no gain in time. framy decodes a picture on one thread per tile (23 and 49 threads, as fast), a sound on one, and decodes and encodes a clip on four, the CPUs the stack gives it: a 1080p clip to 720p then takes 27 threads and 200 MB instead of 71 and 360 MB, and 2.3 s instead of 1.6 s on ten free cores.
  - **Orientation.** JPEG's EXIF tag and HEIF's `irot`/`imir` turn the picture. An orientation written only into a HEIF's EXIF is ignored, as the HEIF rules say and macOS does.
  - **Colour.** An iPhone shoots in Display P3. ffmpeg keeps a JPEG's profile but loses it when it joins a HEIC's tiles, and models and Telegram read pixels as sRGB. framy finds Display P3 itself, by the colorants of the ICC profile (JPEG APP2, PNG `iCCP`, WebP `ICCP`, HEIF `colr`) or `nclx`/`cICP` primaries 12, and has `scale` convert the pixels (`in_primaries=smpte432`, FFmpeg 8.0 or newer) and drop the profile. Other profiles, such as Adobe RGB, are kept as they are. The result matches macOS ColorSync within 1/255.
  - **Alpha.** PNG and WebP keep it. A HEIF or AVIF stores alpha as a separate picture, which ffmpeg does not join, so such a file comes out as JPEG without it.
  - A cut JPEG is shown as far as it goes, as a browser shows it; a cut upload is refused before, by the length of the body.
- **Results** are copied into R2 when ready, since provider links expire. A result that comes as a link is fetched only from a public address (`internal/safehttp`), over HTTPS, up to 512 MB, and must be a picture or a video. Its type, and so its extension, is what its first bytes say when they are a format framy knows (JPEG, PNG, WebP, AVIF, HEIF, GIF, SVG, MP4, MOV, WebM), whatever the provider called it, and the log notes a provider that named another; the provider's type stands only for bytes framy cannot tell.
- **Keys and rows.** Uploads go under `in/<random>.<ext>`, results under `out/<job>-<n>.<ext>` (an SVG of Recraft's vector models `.svg`, its picture size the one its root declares: its `width` and `height`, else its `viewBox`) and a continuation's joined clip at `out/<job>-joined.mp4`, so keeping a run's results again after a crash writes the same objects and adds no rows. A provider gets the link to each input, and a link names its key, so no key holds the person's Telegram id; the row says whose a file is. Files kept by an earlier release are under `u/<person>/in/` and `u/<person>/out/`, and their rows keep those keys. Every file is a row of `asset` with its size, type, SHA-256 and picture size, and a clip's length, frame rate and sound (migration 018; a clip kept before it has none). Its `kind` is `upload`, `result` or `joined`; a joined clip belongs to its job as the results do and goes with them. The object is written before its row and removed before it, and nothing cascades into `asset`: a person or a job with files cannot be deleted before them. R2 refuses a body whose SHA-256 does not match, so a cut write never becomes an object.
- **For Telegram**, the photo goes as a JPEG within those limits (long side at most 2560), and the original goes as a document on demand.
- **Video** (`internal/media`, `video.go`) is sniffed from its first bytes (an `ftyp` box that is not a picture's, or Matroska's EBML: MP4, MOV, WebM, MKV) and probed with `ffprobe`. A frame above 64 MP is refused, and so is a clip over 60 s with no part asked for (`video_too_long`; the upload stays for a cut).
  - **Remuxed only** (`-c copy -movflags +faststart`, `-map_metadata -1` and `-map_chapters -1`, so a phone's location goes) when it is MP4 or MOV, H.264 yuv420p, SDR, upright, at most 1920 px on the long side, 60 fps and 10 Mbit/s, with AAC or no sound.
  - **Encoded again** otherwise: H.264 High yuv420p (`veryfast`, CRF 20, at most 8 Mbit/s), AAC at 160 kbit/s and stereo above two channels, even sizes and square pixels, at most 1920 px and 60 fps, turned upright.
  - **HDR** (PQ or HLG) is tone-mapped to BT.709 with `zscale` and `tonemap=hable` where the build has them, as the image does, else converted by the matrix alone, and tagged BT.709 either way.
  - **A part** is cut with `-ss` and `-t` before the input and always encoded again, since `-c copy` cuts only at keyframes.
  - `width`, `height`, the length, the frame rate and the sound come from `ffprobe` after processing. A provider's result is probed the same way, and kept as it came when it cannot be read.
  - **The last frame** for "Continue" is `-sseof -1 … -update 1` saved as PNG, or the frame 0.35 s before the end when the last one is flat, as after a fade to black. It is kept as a photo, as an upload is, with where it was taken.
  - **The join** (`join.go`) of a continuation is one `-filter_complex`: the clip trimmed after the frame, the new video with its first frame dropped (`trim=start_frame=1`), each scaled into the larger size and padded, at one frame rate, the sound at 48 kHz stereo and `anullsrc` for a part without, then `concat`, encoded as under "Encoded again" and tagged BT.709. It runs as the result is kept, after the result itself, within 2 minutes and the time the job has left; it reads both clips from R2.
- **Sound** (`internal/media`, `audio.go`), a reference for a video model, comes the clip's way: `POST /api/videos/uploads`, then `POST /api/videos`. An MP3, WAV, Ogg, FLAC or ADTS AAC stream is sniffed from its first bytes; an M4A or a WebM is a clip to the sniffer, and one with no picture is taken as a sound. An MP3 not cut is copied as it came, without its tags (`audio/mpeg`); anything else, and any part, becomes a 16-bit WAV at 48 kHz, in stereo at most (`audio/wav`). The limits are a clip's: 60 s without a part asked for, and a part cut exactly. A clip with a picture stays a video.
- **`file_id`s** are kept for as long as the generation exists. They are cheap and make inline mode and resending free.
- **Where (owner, 26 October evening):** every input and result is in Cloudflare R2, in a private bucket `framy` with the location hint `eeur`. ws04 keeps only working files: what ffmpeg is processing and what the bot is sending by local path. They are deleted once the job is done.
- **Why R2 and not the ws04 disk.** Cloudflare's policy on delivering video says that on Free, Pro and Business, traffic of a Tunnel's public hostname falls under its limit on video and on "a disproportionate amount" of large files. Files served from R2 are exempt. R2 also takes the files off the home uplink, serves `Range` requests for seeking, and gives up nothing on egress.
- **Price** ([R2 pricing](https://developers.cloudflare.com/r2/pricing/)):
  - storage: 10 GB-month free, then $0.015 per GB a month (100 GB ≈ $1.35, 1 TB ≈ $14.85);
  - writes: 1 million a month free, then $4.50 per million;
  - reads: 10 million a month free, then $0.36 per million;
  - traffic out: free.

  A free-tier user at the limit adds about 250 MB a month, so 10 GB is about 40 such months. People on their own keys add more, and that is what the price per GB covers.
- **Serving:**
  - private results go through presigned GET URLs. They work only on `<account>.r2.cloudflarestorage.com`, which has no Cloudflare cache, but its egress is free too;
  - a link is signed as of the start of the hour it is made in and lives that hour and 10 minutes more, so every view of a file within the hour gets the same URL and has 10 minutes at the least. It asks R2 for `Cache-Control: private, max-age=4200` (`response-cache-control`), so the browser keeps the file as long as the link lives and the library opened again within the hour loads nothing. A picture of the library whose link ran out makes the page read its run again for new links, at most once in 10 minutes for a run, so a tab open for hours keeps its pictures. The cache is the person's own browser; a file they delete may still show from it until the link dies;
  - **thumbnails** (migration 024): each result and joined clip has a WebP at most 480 px on the long side, of a video its poster frame (the one the chat's card shows), at `out/<job>-<n>.thumb.webp`, beside its result. It is made from the local file as the result is kept; a failure keeps the result without one. A loop at start and every minute makes the ones results lack, newest first, each tried three times: results kept before thumbnails, and failures. It counts the try on the row and holds no lock while it reads, encodes and puts the file, so a person deleting the result never waits for it: a delete removes a thumbnail the row names only as it goes, and the loop deletes a thumbnail it made for a result that went meanwhile. A thumbnail counts in the person's storage and the bucket's. An SVG gets none, as it is kept or later: ffmpeg does not draw one, and the file is small and sharp at any size, so the site shows it as it is, in an `<img>`, where an SVG runs no script and loads nothing. Opened by its own link it runs on R2's origin, which holds no cookie or session of framy's. It needs the libwebp encoder, which framy's image has; without it results get none and the API shows no `thumb`;
  - public result links, if they come, use a custom domain on the bucket. It must be a first-level name such as `framy-media.ws04.cc`, since Universal SSL does not cover `media.framy.ws04.cc`.
- **Uploads from the site** happen on Create, not on attach (see Attachments):
  - photos come through the service, under Cloudflare's 100 MB per request;
  - a clip goes by presigned PUT straight into `incoming/<person>/<token>` (`POST /api/videos/uploads`), which a lifecycle rule clears after a day. framy checks the size with HEAD, reads the object into its working directory, runs it through the video pipeline, writes the result under `in/` and removes the incoming object. A clip framy cannot take is removed at once; one that is only too long stays until it is taken with a part, or the day ends.
  - the link signs the host and the length the client asked for (`X-Amz-SignedHeaders=content-length;host`), and R2 refuses a body of any other length: a link holds the one clip it was made for, never the 5 GiB R2 takes in a PUT, however often its holder uses it in its 10 minutes. R2 checks the link when a PUT begins, so a slow upload that started in time still ends; a try that failed asks for a new link. `go test -tags r2live -run LivePresigned ./internal/r2` checks the real bucket refuses another length. A browser sets `Content-Length` itself, so the bucket's CORS rule needs nothing more. Any other header is not signed, so whoever holds the link may add one. On S3 a header such as `x-amz-copy-source` would make the PUT a copy of any object the signing token reads, and the person would get someone else's file as their own upload; R2's docs do not say whether it refuses an `x-amz-*` header the signature does not cover. `go test -tags r2live -run LiveCopySource ./internal/r2` asks the real bucket. So that the answer does not matter, clips can go into a bucket of their own, `R2_INCOMING_BUCKET`, with a token that has Object Read & Write on it alone (`R2_INCOMING_ACCESS_KEY_ID`, `R2_INCOMING_SECRET_ACCESS_KEY`, each also as `_FILE`, read only with the bucket): a copy from any other bucket is then refused. The bucket needs the same lifecycle rule on `incoming/` and a CORS rule for PUT with a `Content-Type` from both sites, the one request the browser makes to it; `TestLiveIncoming` checks the PUT from both and that the token reads nothing of `framy`. Without it clips go into `framy`, as before.
- **To providers**, input photos go as presigned R2 URLs instead of base64, where the API takes a URL (OpenRouter's `input_references`, OpenAI's `images[].image_url`).
- **The bucket's CORS** allows PUT, GET and HEAD from `https://framy.ws04.cc` and the test stack's `https://framy-test.ws04.cc` (30 October) with a `Content-Type`, and GET and HEAD for the Telegram Web origins, so `downloadFile` works. `Content-Disposition` comes through `response-content-disposition` in the presigned URL.
- **Keys:** an R2 API token limited to framy's bucket, as a file secret like the KEK, and the clips' bucket's own token when it is set (Uploads from the site). The account token `framy` (27 October) has Object Read & Write on `framy` and `framy-backups`, no expiry and no client IP filter, since the links it signs are opened from people's browsers. It needs `framy` alone: nothing of framy's writes to `framy-backups` (Backups). Its halves are `r2-access-key-id` and `r2-secret-access-key` in the stack's secrets on the home server, root-only, the same for both stacks. `go test -tags r2live ./internal/r2` checks it against the real buckets: objects, presigned links with the browsers' `Origin`, a copy a link must not make, and a refusal in `framy-backups` and in another bucket of the account (`R2_FOREIGN_BUCKET`); the refusal in `framy-backups` fails until the token loses it.
- **Turned on:** R2 was activated on 26 October as a $0 subscription on the account that holds `ws04.cc`, with the card already on file. Usage above the free allowance is billed to that card monthly.
- **How long (owner):** until the person deletes it: one result, or the whole account from the settings. Deleting removes the objects and the rows at once; the `file_id`s go with them.
- **Deleting a job** (`DELETE /api/jobs/{id}`, migration 017) takes its results and the uploads no other job of the person's that is not deleted takes; an upload two jobs share stays with the other one. Each upload goes in a transaction that locks its row (`FOR UPDATE SKIP LOCKED`), as the sweep does, the object first and then the row. The job's row stays, with `deleted_at` set and the prompt, the settings, the error with the provider's own words, the grounding and the chat cleared (migration 034 cleared the provider's words of the jobs deleted before they were): the free allowance and its daily budget are counted from job rows, so deleting a run does not give its free slot back. A result the site sent to the DM stays in the DM, and its `site_delivery` row stays `sent` without the message's id. A result on its way to the DM at that moment is held behind the delete: `SentSiteResult` locks the job's row, and a job deleted by then gets neither the message's id nor a chat run. A file that would not go keeps the job as it was, and the delete can be sent again.
- **A deleted job in a chat.** Its `chat_run` goes with it, and a result already sent stays in its chat. A preview or a generating loop still in a chat (a job that ended a moment before the delete, or a draft the account's deletion cancelled) is left for that stack's bot: within 2 s, the time it takes to look at its runs again, it deletes the message and the Model and Settings panel, as No does, and drops the run. A guest answer cannot be deleted and says "Deleted." with no buttons. Until then no button of the run works and no card of it is drawn; only the clip it pointed at is cleared at once. Each look reads only the runs still open, which an index finds; a run that moved on in the moment its job went, its result in the chat already, is dropped by the look at every run the bot takes when it starts and once an hour.
- **Deleting the account** (`DELETE /api/me`) goes in this order, so a failure half way can be sent again and carries on from what is left:
  1. it is refused while a job is queued or running. The site then offers to cancel the queued ones and says how long the started ones take: an image a few minutes, a video up to the run's hour;
  2. every file of the person's that existed when the deletion began goes, 8 objects at a time, each object before its row; the work goes on for up to 4 minutes when the client leaves. The clips they put by link that framy never took go too, found by listing `incoming/<person>/`; one the bucket would not list or delete is left to the lifecycle rule, which takes it within the day;
  3. in one transaction, under the lock under which a job of the person's is created, queued and claimed (`jobs.LockPerson`, taken before the free allowance's), and refused if a job is queued or running by then: a job pressed meanwhile in the bot or another tab is either seen here or made after, as by a person who came back, never half way with its files gone and its prompt kept. Then drafts are cancelled, every job is cleared as one deleted alone is (with its chat runs and the ids of the DM messages its results went in) and given the time it stops saying whose it was (below), and the keys, the pending OpenRouter connections, the profile (currency, name and photo) and the album photos framy saw the person send in a chat are deleted;
  4. the files kept since step 2 go too: a run pressed after step 1 that ended before step 3 kept its results then, and step 3 has cleared its job. A file kept after step 3 is a new run's, of a person who came back, and stays. When this fails the sessions stay, and sending the deletion again carries on;
  5. the language the person picked in framy is withdrawn from core;
  6. every session of the person's goes, on the site and in the Mini App, on both stacks, and every process of framy forgets them at once.

  The person's row in `core.person` stays: it belongs to the family, and coming back to framy starts afresh, with the free runs still in their window counted. A result already sent to a Telegram chat stays in that chat.

  The account's jobs keep the person's id only as long as the allowance needs it (migration 035): a free run until it leaves its window, a day after it was queued for an image and a week for a video, and every other job not at all. Then, within the hour, `user_id` becomes NULL, and the row keeps its kind, cost and times, which the day's budget counts, and says nothing more of whose it was. A run whose preview is still in a chat keeps the id until the bot has taken the message down, which it does by the person's id. Only a deleted job may be without a person. A job deleted alone, by a person who keeps the account, keeps the id: what was spent with a key is counted from it.
- **Accounting.** framy sums the bytes per person in `asset`, shows it in the settings and tells the operator chat (`OPERATOR_CHAT_ID`) each time the bucket passes another 10 GB, the first being where the free allowance ends. A write sums the whole bucket at most once a minute, since the sum reads every file's row; a write that came sooner is summed by production's check a minute later, so a step the last write of a busy minute crossed is told then and does not wait for the next write. The last step told is kept in `runtime_state`; two writes crossing it at once tell it once, and a message that failed is tried again by the next write or that check.
- **Working files** live under `WORK_DIR`, a directory per upload or result removed when its work ends, failed or not. Whatever is older than an hour is swept at start and every hour.
- **Uploads no job took** are deleted after an hour, the object first and then its row, at start and every hour (`Store.SweepUploads`), looked for 100 at a time. An upload is taken once a job lists it in `job_input`, and then it stays until the person deletes it like any file. The sweep locks the row while the object goes, so a job taking the file at that moment either keeps it or is refused as if the file were not the person's.
- **A draft that never ran** (No, or ten minutes without Create) keeps nothing the person wrote or sent, since nobody can come back to it and the history does not show it. Right before the uploads are swept, `jobs.Queue.ClearDrafts` clears it as a deleted job is cleared (the prompt, the settings, the chat) and lets go of its files (its rows of `job_input`), so the photos and clips only it took go in the same sweep. It waits for the chat to close the draft's preview, up to two days, after which Telegram would not let the bot delete the preview anyway.

## Security and operations

Details and sources in [research/build.md](research/build.md).

- **Headers.** One CSP for every HTML route. It has `frame-ancestors https://web.telegram.org https://webk.telegram.org https://weba.telegram.org` and no `X-Frame-Options`, which would conflict with the Mini App iframe. `img-src`, `media-src` and `connect-src` allow `https://<account>.r2.cloudflarestorage.com` for presigned files and uploads, and `img-src` also `https://t.me` and `https://*.telesco.pe` for the person's photo. `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `Cross-Origin-Opener-Policy: same-origin` on every response, and HSTS for a year. Before launch, check that Rocket Loader, Web Analytics and email obfuscation do not inject scripts the CSP would block.
  - `internal/web` builds the policy once at start and adds it to any response that is HTML, XHTML, SVG or names no type. There is no nonce: the frontend's scripts and styles are files served from the site's own `/assets/`, and an inline block is added by hash (`web.InlineHash`, `Config.CSPExtra`). Besides the R2 origin, `script-src` has `https://telegram.org/js/telegram-web-app.js` and nothing else from outside.
- **CSRF:** `http.CrossOriginProtection` from Go 1.25 around the mux, with a bypass for `/hooks/…`. No state changes on GET. A browser that sends neither `Sec-Fetch-Site` nor `Origin` is taken for a client that is not a browser, and one that sends only `Origin` is checked against `Host`, so the tunnel must pass the original `Host` on. A route that has to take a cross-site POST is added to `csrfBypass` in `internal/web`.
- **Cache.** By default Cloudflare caches by extension, not by cookie:
  - `/api`, `/auth`, `/oauth` (the OAuth callbacks), `/events` and `/hooks` send `no-store`, whatever the handler says;
  - hashed assets send `public, max-age=31536000, immutable`: files under `/assets/` with eight or more hex digits before the extension (`app.3f9a1c2b.js`) or a hex `?v=`, on a 200, 206 or 304 only. An unhashed file there is `no-cache` and an error `no-store`. Public result images follow once they exist (`PublicCache`);
  - private results send `private, no-store` and never `public`: `public` from a handler is rewritten unless its route opted in;
  - HTML with no `Cache-Control` of its own gets `no-cache` (revalidate by ETag) and everything else `no-store`, so nothing is cached because nobody said;
  - the zone's Browser Cache TTL was meant to be "Respect Existing Headers", as maply's `?v=hash` lesson showed. On 31 October ws04.cc had 4 hours, and framy is not touched by it: every answer carries its own `Cache-Control`, and Cloudflare passed `no-cache`, `no-store` and the year of a hashed asset unchanged (`curl -I` through framy-test.ws04.cc: the page, `/api`, `/share`, an asset, a 404). A Cloudflare setting that rewrote them would show in the same check.
- **`downloadFile` in the Mini App.** Telegram Web fetches the file from its own page, so the answer needs `Content-Disposition: attachment` and `Access-Control-Allow-Origin` for it. Every download framy gives is a presigned R2 link (`download` in the API): the attachment comes from `response-content-disposition` in the link, and the CORS from the bucket's rules (Storage and retention), which on 5 November answered a preflight from `https://web.telegram.org` and `https://webk.telegram.org` with GET and HEAD and refused another origin. The service itself sends no CORS headers, so a download it served from its own routes would fail in Telegram Web: such a route has to reflect those origins in `Access-Control-Allow-Origin` with `Vary: Origin` first.
- **Rate limits.** Cloudflare Free gives one rate-limit rule and 5 WAF rules, and Bot Fight Mode cannot be skipped by rules. So the limits live in framy:
  - token buckets per person and per IP (`x/time/rate`, in memory, in `internal/web`). Every request is counted in the default class by address; a route in another class is counted there too:

    | Class | Routes | Per address | Per person |
    |:--|:--|:--|:--|
    | default | everything | 30/s, burst 120 | none |
    | auth | `/auth`, `/oauth` | 20/min, burst 10 | none |
    | miniapp | `POST /auth/miniapp` | 120/min, burst 60 | none |
    | upload | `Limit(ClassUpload)` | 40/min, burst 40 | 20/min, burst 20 |
    | job | `Limit(ClassJob)` | 20/min, burst 20 | 10/min, burst 10 |
    | hook | `/hooks` | 20/s, burst 100 | none |
    | health | `/healthz` | 1/s, burst 10 | none |

    The numbers are guesses to be set from real traffic. An IPv6 visitor is counted by its /64. The person is whoever `Config.Person` names (`auth.PersonKey`), asked only on routes whose class has a per-person bucket; nobody signed in is counted by address alone. A refusal is a 429 with `Retry-After` and `framy_http_rate_limited_total{class}`, except on the routes a browser navigates to (`GET /auth/login`, `/auth/callback`, `/oauth/openrouter/start` and `/oauth/openrouter/callback`, `web.OnLimit`): they send it back to the site with `?sign_in=unavailable` or `?connect=openrouter&result=unavailable`, which says to try again in a few minutes, instead of a bare page with no way back;
  - quotas in Postgres;
  - the real IP from `CF-Connecting-IP`, believed only when the TCP peer is in `TRUSTED_PROXIES`, the address cloudflared connects from. On ws04 that is cloudflared's own address, fixed in the tunnel's stack, not the range of its network: `management` holds every site of the host, 14 containers on 5 November, and any of them could otherwise write the header and pick its own address for the limits. Not done on 5 November: cloudflared had no fixed address yet, so both stacks still trusted the range. From any other peer the header, `X-Forwarded-For` and the rest are ignored. The service must publish no port to the host, or the userland proxy hides the visitor behind the gateway address.

  Bot Fight Mode stays off for the framy hostname, or OpenRouter's webhook POSTs get challenged.
- **Uploads** through Cloudflare are at most 100 MB per request. Photos come to the service; videos go by presigned PUT straight into R2 (see "Storage and retention").
- **Outgoing requests** to URLs from providers go through a dialer that refuses private addresses (SSRF).
- **Database connections** (`db.Connect`). core-postgres is shared with the family's bots and with the other stack, so a process keeps at most 8 connections and closes one left idle for 5 minutes. They are named `framy`, or `framy-<stack>` for another stack, and the event listener's `framy-events` or `framy-<stack>-events`, so `pg_stat_activity` tells production from the test bot. A statement ends after 30 s and a transaction left open with nothing running in it after 10 minutes, with the locks they hold. The migrations run under limits of their own (Stacks), and the wait for another process's migrations has none. `pool_max_conns`, `pool_max_conn_idle_time`, `statement_timeout`, `idle_in_transaction_session_timeout` and `application_name` in `DATABASE_URL` win over these.
- **The container's own files** are read-only on both stacks (`read_only: true`), with a 64 MB tmpfs at `/tmp`: everything framy writes lives in `WORK_DIR`, `ANIM_CACHE_DIR` and the Bot API link, all mounts, so code that runs through a flaw in a decoder (ffmpeg and the image libraries read people's files) cannot leave a file in the image. After days of running, `docker diff` on production showed nothing in the container's layer but the mount points. CI runs the media tests in the image under the same rule (`--read-only`, a tmpfs at `/tmp`), so a new write outside the mounts fails there and not first in production.
- **Backups:** framy makes none of its own. Its tables live in core-postgres, which the home server's daily backup (`ws04-backup.timer`, 05:30) dumps whole with `pg_dumpall`, the `framy` schema and the `framy_core` role with it, into an encrypted restic repository of its own on Google Drive, keeping 7 daily, 4 weekly and 6 monthly snapshots, as for every service on the shared database. That copy is the owner's, out of reach of framy's R2 token, so a leak of the token or of the test bot cannot take the data and its copy together. The same backup copies `/opt/stacks`, where the stacks keep their manifests, `.env` and `secrets/`, into another repository under the same password, so it has to leave out the KEK: `secrets/kek` of both stacks and any copy of it beside them. Whoever can open the backups must not hold what opens the keys in them. On 6 November it does not: the stacks' repository takes `/opt/stacks/framy/secrets/kek` and `/opt/stacks/framy-test/secrets/kek` with the rest **(owner:** leave both out in `/opt/ws04-backup/backup.py`, keep the copy elsewhere, then rotate the KEK, since the snapshots kept so far hold the current one**)**. Proposal: the copy of the KEK that brings the keys back after a lost disk is kept in the owner's password manager and replaced at each rotation. Not done on 5 November (#28): a restore of the schema from the dump into an empty database has not been tried. Nothing of framy's writes to the R2 bucket `framy-backups`, and the service's token needs no access to it (Keys); the first plan, a dump of `framy` alone into it, encrypted with `age` and kept 30 days, is not built, and beside the host's backup it would only add a copy at another provider. A dump framy wrote itself would go there with a token that may only write, under a bucket lock rule. Objects in `framy` are not backed up: R2 is their copy off the home server. The files of `telegram-bot-api` need cleaning by age; how much it keeps is not checked.
- **Logs** are JSON lines on stdout, read with `ws04 logs framy-bot`. River, the job queue, writes a producer's counts and each maintenance pass at Info every minute, which was 97% of production's log, so its own lines are kept from Warn up unless `LOG_LEVEL` is `debug`. A job's attempt that failed on framy's side (the database or the bucket not answering), which River writes at Info, is framy's own line instead: `job attempt failed` as a warning, or `job attempt panicked` as an error, with the framy job, River's attempt and the error with presigned links taken out.
- **Metrics** on a listener of their own (`METRICS_ADDR`, `GET /metrics`, `internal/metrics`), which the stacks bind to `127.0.0.1` inside the container: the page holds the spending by model and payer, and the container's networks hold some 35 others. A scraper, once there is one, gets a network of its own. Beside the process counters:
  - `framy_job_cost_usd_total{provider,model,payer}`: what the providers billed for the jobs that ended, `payer` being `free` (framy's key) or `key` (the person's);
  - `framy_job_duration_seconds{kind}`: a histogram of the time from the queue to the result of the jobs done, 5 s to an hour;
  - `framy_job_failures_total{reason}`: the jobs that ended without a result, by their error class (`moderation`, `provider`, `timeout`, `money` and the rest), the sweep's included;
  - `framy_jobs{status}`: the jobs queued and running, read from the database when the page is asked for;
  - `framy_sse_streams_open`: the event streams open now;
  - `framy_busy_total{what}`: the requests answered 503 `busy`, by what was full: `photo_slots` (every photo conversion, for 20 s), `photo_person` (2 photos of the person's coming in), `clip_queue` (16 clips of everyone's), `clip_person` (3 of the person's), `clip_slots` (a last frame waited 20 s). The first time in a UTC day that `photo_slots`, `clip_queue` or `clip_slots` was full, the operator chat hears it as well; a restart that day may tell it again;
  - the process and the Go runtime under the names Prometheus's Go client gives them, so a dashboard made for any Go service reads them: `go_goroutines`, `go_memstats_heap_alloc_bytes`, `go_memstats_sys_bytes`, `process_start_time_seconds`, and from `/proc` on Linux `process_resident_memory_bytes`, `process_open_fds` and `process_cpu_seconds_total`. A video is held in memory while it is copied, up to 128 MiB a worker, under the container's limit of 1 GiB: these show memory or goroutines piling up before the container is killed for it.

  The job counters start from zero with the process, as a scraper expects of a counter; the database keeps the whole history. Each stack's process counts only its own stack's jobs, so production's and the test bot's pages add up to the whole and never count a job twice; the sweep, which runs on River's leader and ends either stack's drafts and abandoned jobs, writes a failure of the other stack to the log only. Each job keeps a snapshot of the price it was estimated with. The operator chat (`OPERATOR_CHAT_ID`, production only) hears when a fuse closes the free tier (the day's budget, or `limit_remaining` of framy's OpenRouter key), each time the `framy` bucket passes another 10 GB, and what the watch finds. Without one, production still takes each of those steps once and logs it at Warn, and its start warns that the notices are only in the log. Nothing scrapes `/metrics` yet: the counters are read by hand, from inside the container.
- **Health** (`internal/health`): `/healthz` on the public listener answers 200 `{"ok":true}` or 503 `{"ok":false}` and nothing more. The tunnel makes it public and the repository is open, so the commit that runs and the part that fails are not for everyone; Docker's healthcheck and a watch from outside need only the answer. The same check with its parts answers on the metrics listener, `GET /healthz` beside `/metrics`, always with 200, since busybox's `wget` in the image prints no body of a 503: `ok`, `version`, `commit`, `built_at`, `db`, `telegram_initialized`, `telegram_polling_fresh` with `telegram_last_poll_at`, `telegram_last_update_at`, and `telegram_calls_failing` with `telegram_last_answer_at` and `telegram_last_failed_at`. It is OK when the database answers, the bot has started, getUpdates answered in the last 90 s, and calls to Telegram are not failing.
  - **Calls to Telegram.** The family's Bot API in `--local` mode answers getUpdates from the host even when it has lost Telegram, so polling stayed fresh on production through the outage of 3 November. Calls fail when, for two minutes, every call but getUpdates ended without an answer or with a 5xx, the last of them in the last five minutes; a call that got through ends it. A 4xx or a 429 counts neither way, since the local server gives some of those from what it knows. A bot nobody uses makes no calls, so a lost Telegram shows only once framy has something to send.
  - `telegram_last_update_at`, when the last update came, is a clue for whoever reads it and not part of the check: a quiet night brings none.
  - Unhealthy is a mark for whoever looks (`ws04 container list`, a watch from outside): Docker does not restart on it, and a restart would not bring Telegram back. A queue that nothing takes from is the watch's, below.
- **Watch** (`internal/watch`): once a minute each stack looks at what `/healthz` does not show, and production tells the operator chat:
  - the disk under `WORK_DIR`, the host's own, past 80, 90 and 95%: each step once on the way up, and again only after the disk fell two points below it;
  - jobs of its own queue that could have started 10 minutes ago and that nothing took: the person had a free slot on that stack (a video out at the provider holds none, as in a claim), nothing of theirs was ahead there, no refusal had it wait. A working queue takes such a job within seconds, so it means the workers are gone; the chat hears when it starts and when jobs are taken again. The first look is a minute after the start, so jobs left from the previous process are not counted.

  The watch keeps what it told in memory, so a restart tells a standing problem once more. A framy that is down, or up and failing `/healthz`, cannot tell anyone, and Docker does not restart an unhealthy container. That is for a watch from outside, on `https://framy.ws04.cc/healthz` and the test bot's. The host already has one: the Cloudflare Worker `ws04-watch` asks `https://ws04.cc/healthz` every two minutes and tells the owner in Telegram when the server stops answering and when it is back, so an outage of the whole server, its power or its internet, is told. It told the one of 3 November, when the home network was offline from 12:57 to 14:00 UTC: framy could reach neither OpenRouter nor Telegram, kept its saved catalog and rates, let the fuse on its key go by the day's budget alone, and picked up on its own: the key and the test bot's polling within a minute of the network, the rates and the catalog at their next try. A second DNS server would not have helped, since nothing reached the internet by address either. What the Worker does not see is a framy that is down or unhealthy while the server is up. Proposal: the Worker asks both framy stacks too.
- **Deleting an account** removes the rows, the files and the encrypted keys at once.

## Architecture

```text
framy (Go, one service on ws04)
  ├─ HTTP: site and Mini App statics, API, SSE, OAuth callbacks, provider webhooks
  ├─ bot: long polling through tg, /img and /edit, album cache, delivery
  ├─ workers: jobs in Postgres, provider adapters (openrouter, openai, gemini), result download
  ├─ catalog: hourly OpenRouter sync, local descriptors and overlay, daily FX rates
  ├─ price: the estimate before a run, from the catalog's rates
  └─ renderer: loops and previews (internal/anim, from maply), error and preview cards

telegram-bot-api (--local), sharing a volume with framy
core-postgres: framy schema; identity and language from core
Cloudflare R2: bucket framy (inputs and results), and the clips' own bucket when one is set
ws04-backup, the host's, daily: core-postgres with the framy schema, to Google Drive
Cloudflare Tunnel: framy.ws04.cc
```

`maply/internal/anim` cannot be imported from another module, so framy copied what it needs: the canvas, the text shaping and the encoder pipe. Proposal: extract a shared module once both projects change them.

The `framy` schema and its `framy_core` role come from core migration `019_framy.sql`, as maply's from 018. The tables in it are framy's own: its migrations (`migrations/`, embedded in the binary and recorded in `schema_migrations`) create them, and River's migrations (`jobs.MigrateRiver`, run after framy's) add River's `river_*` tables beside them.

| Table | What it stores |
|:--|:--|
| `profile` | `user_id`, currency (#8), whether framy picked the language (the language itself is core's, shared with the other bots), the default image and video models, delivery to Telegram (migration 025), and the name and photo the site shows (migration 012) |
| `session` | a sign-in: the SHA-256 of the secret the browser's cookie or the Mini App's bearer token holds, never the secret, with the person, `site` or `miniapp` and the expiry (migration 008) |
| `connection` | provider, encrypted key with its wrapped data key and KEK version, `last4`, status, last success, last error class; one per person and provider |
| `catalog_model`, `catalog_offer` | models with the overlay's flags and traits; offers with their parameters, routes and prices, `expires_on`, `hidden`, `fetched_at`, `disabled_at`. The hourly sync writes a row only when something in it differs, so `fetched_at` and `updated_at` say when the offer last changed, and the sync's own time is `runtime_state.catalog_synced_at` |
| `job` | requester (`user_id`, NULL for a deleted account's job once its `forget_at` has passed), surface, chat and preview message, `dedupe_key`, offer, prompt, settings, `free`, status, idempotency key, River job, paid requests with `submitted_at` and `retry_at`, provider job id, the estimate with its lines, the actual cost, results, error class with framy's line and the provider's own words, the currency with `fx_rate` and `fx_date`, the stack that made it (`stack`, migration 029), the press of the site it belongs to and the frame of each result (`batch`, `batch_frames`, migration 030), and when the person deleted it (`deleted_at`) |

| `job_input` | the files a job takes, in order; an empty place is a file deleted before the run |
| `chat_run` | a job started in a chat (migration 014): the chat and its topic, the command, the preview and whether it or the command is ephemeral, the answer of guest mode (`inline_message_id`), the language, what was taken of an album, the stage from preview to done, Stop, the result's message, `file_id` and which file it is (`result_asset_id`), the clip of `/edit`, and the bot whose chat it is (`stack`) |

## Stacks

Production (@framyin_bot, framy.ws04.cc) and the test bot (framy-test.ws04.cc) share the `framy` schema in `core-postgres` from v0.1.0-alpha.2 (owner, 31 October 2026): one history per person on both sites, one free budget, one catalog, one key per provider. `FRAMY_STACK` says which process is which: empty for production, `test` for the test bot. Migration 029 keeps apart what only one bot can act on:

- **Queues.** A stack other than production puts its name before each River queue (`test_openrouter_image`, `test_default`) and works only those. `job.stack` is the stack that made the job, and its run waits for that stack: while the test bot is stopped, its jobs stay queued, and its runs at a provider stay running. A person's limit of runs at once, and their turn in it, are counted on each stack apart, so what a stopped test bot left behind holds up nothing of the same person's on production; a job that ends wakes the next one waiting on its own stack.
- **Telegram.** Message ids are counted per chat and per bot, a person's DM with each bot has the same chat id, and a `file_id` works only for the bot that got it. `chat_run.stack` and `album_item.stack` name the bot. A process follows, delivers, answers inline and reads albums only from its own; Send to Telegram reuses a stored `file_id` only from its own bot and uploads the file otherwise. A Telegram dedupe key of a stack other than production has its name after `tg:`.
- **getUpdates.** Production keeps its offset in `runtime_state`, where every release has read it; any other stack in `stack_state`.
- **Site results.** A result made on a site goes to the DM from that site's bot, by `job.stack`.
- **Sessions** (migration 032). A site's cookie and a Mini App's token work only on the stack that made them (`session.stack`): what the test bot signs, running code not yet released, signs nobody in on production. Sign out everywhere and a deleted account end a person's sessions on both, and the other process forgets the ones it remembered on the notice that comes with the delete (Accounts). The OAuth flow of a provider is one per person over both sites (`oauth_state`, keyed by person and provider): starting it on one site ends one begun on the other within its ten minutes, whose callback then asks to start again. Sessions made before migration 032 are production's, so a person signed in on the test bot signs in there once more.

Production alone keeps what both would share: the catalog sync, the currency rates, the clearing of drafts that never ran and the sweep of uploads no job took, the album cache's sweep (so the photos people send go after 48 hours while the test bot is stopped too, and code not yet released does not decide when production's go), the thumbnails, the sweep of sessions and Mini App tokens that expired a day ago (at start and every hour; an expired one is never accepted, so this only keeps `framy.session` small), the forgetting of whose a deleted account's jobs were (at start and every hour, `Store.ForgetJobs`), the rotation of the KEK (Keys at rest) and the operator chat (the bucket's steps, the free tier's fuses). Expired sessions and OAuth flows, and webhook deliveries older than a week, are also deleted on the way by whichever process signs a person in, starts a flow or takes a webhook: each is one indexed delete of rows nothing uses any more, and either stack doing it keeps them few while the other is stopped. Two releases would write their own catalog over each other every hour, so a catalog change on `dev` reaches the test bot with the release that takes it to production. River elects one leader for the schema, and the leader's sweep of drafts and stale jobs serves both stacks.

The test bot is inside production's perimeter, by the owner's choice of one schema: it holds the same KEK, so it reads every key people connect, the same R2 token on the same keys, so it reads and deletes every file, and the same database role. What keeps unreviewed code off production's data is the image it runs: a published pre-release of `dev` that passed CI (docs/releases.md), pinned by digest as production's is. A build of any other commit acts on production's data as a deploy to production would.

The test bot runs `dev`, so its migrations reach production's schema before production's binary knows them. A migration must leave the released binary working: new tables, columns that are NULL or have a default, indexes. It runs in one transaction under `lock_timeout` 5 s and `statement_timeout` 1 min, so a migration queued behind a long transaction gives its lock back and is tried again a few times instead of holding every query to the table behind it; a new CHECK on a table with rows goes in `NOT VALID` and is validated later. `schema_migrations` keeps the SHA-256 of each file, and a file changed after it was applied stops the start. A rename, a drop, a changed type or key, or a new NOT NULL without a default waits until production runs a release that no longer needs the old form, and so does an upgrade of River that brings migrations of its own. Two tests hold it: `TestMigrationsAreAdditive` (`migrations/`) refuses a migration that drops, renames or retypes, makes a column NOT NULL, takes a default away, or adds a constraint, a unique index or a NOT NULL column without a default to a table that has rows, unless the migration says in a line `-- not additive: …` why the released binary still works or which release production runs first; and `TestRiverBringsNoMigrationProductionLacks` (`internal/jobs`) fails when the River framy is built with goes past the last River migration production's schema has, so an upgrade from Dependabot, which comes in a pull request of its own, stops until someone has read it. Migration 029 itself changed `album_item`'s key, so v0.1.0-alpha.2 went to production before the test bot moved onto the schema, and production cannot roll back to v0.1.0-alpha.1 without losing the album cache's writes.
